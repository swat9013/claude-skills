# inventory-harness

実行中 repo の harness (permission / CLAUDE.md・rules / skill・MCP / project の規範 / 呼出数・本文の変更・注入字数で選んだ skill の記述と本文) をまとめて棚卸しする。plant ごとの観測と分類は各棚卸し skill の手順を subagent に走らせ、人に示す段から後 (提示・承認・反映・照合) は本 skill だけが持つ — 並行に走る側は人に問えず、書く側を 1 つにすれば同じ file への並行の書き込みが起きない。

4 段階モデル (原則: **観測・集計は決定的に、判断は人間に、LLM は候補の統合と根本課題の仮説まで、反映は承認分だけ**):

1. **plant ごとの観測と分類** (手順 1・2): subagent が各棚卸し skill の節「返却」に従い、分類まで進めた候補を返す
2. **統合** (手順 3): 複数の候補を説明する原因を根本課題として挙げ、反証を通す
3. **人間判定** (手順 4): 根本課題と候補を 1 ラウンドで示し、人が答える
4. **反映** (手順 5〜7): 採られた根本課題と Computational 化の束を起票し、承認された候補だけを書く。**人間承認を得ていない write はゼロ**で (自律で直す一覧の候補は、人が番号で外さなかったことを趣旨の承認とする)、書き終えたら全 diff を提示する

対象外: plant ごとの観測・分類の中身 (各棚卸し skill が持つ)、harness の文面の規範 (`write-for-harness` が持つ)、根本課題の解決 (起票で止める)。変更の届け方は実行 project の運用に従う。

## 手順

### 1. plant の棚卸しを並行に走らせる

起動の前に、この実行の置き場 `/tmp/inventory-harness/<実行開始の時刻 (秒まで)>/` を作る (以下 `<run-dir>`。並行する実行と file が混ざらないようにする)。時刻は先に `date +%Y%m%d-%H%M%S` を実行し、得た値を path に直書きする。親の `/tmp/inventory-harness/` は `mkdir -p` で、`<run-dir>` は `-p` なしの `mkdir` で作り、既に在れば時刻を取り直す。続けて `${CLAUDE_SKILL_DIR}/../write-for-harness/references/caller-contract.md` を Read し、「委譲後の変更 path の照合」節の 1 のとおりに git の状態を控える — subagent は script の実行・観測の invoke・レポートの書き出しが要るので tool を絞れず、書き込める tool を持ったまま走る。書き換えていないことは、手順 1・2 のそれぞれの終わりに確かめる。git から見えない書き先 (`~/.claude/settings.json`・cwd の `.claude/settings.local.json`・cwd の `CLAUDE.local.md`) は `<run-dir>` へ複写して控え、無い file は「不在」と控える。`~/.claude.json` は Claude Code 自身が書くので file ごとは控えず (控えると照合が毎回止まる)、top-level の `mcpServers` と `projects.<cwd の絶対 path>.mcpServers` の値だけを `<run-dir>` へ書き出して控える。

次の 4 本を、`Agent` tool の `subagent_type: general-purpose` で同じ message に並べて起動する。`name`・`model`・`effort` は渡さない。

| plant | Read させる SKILL.md |
|---|---|
| permission・sandbox・guard hook | `${CLAUDE_SKILL_DIR}/../inventory-permissions/SKILL.md` |
| CLAUDE.md・rules | `${CLAUDE_SKILL_DIR}/../inventory-claude-md/SKILL.md` |
| skill・MCP の存廃 | `${CLAUDE_SKILL_DIR}/../inventory-skill-mcp/SKILL.md` |
| 実行中 project の規範 | `${CLAUDE_SKILL_DIR}/../inventory-project-values/SKILL.md` |

prompt は次の 1 文だけにし、path は展開後の絶対 path を書く (subagent の側では変数が展開されない)。観測と分類の手順・返す形は各 SKILL.md が持つので、prompt に書き写さない。

```
<SKILL.md の絶対 path> を Read し、節「返却」に従って cwd の repo の棚卸しを進め、結果を返す。本文の `${CLAUDE_SKILL_DIR}` は、その SKILL.md があるディレクトリの絶対 path に読み替える。
```

全 subagent の最終報告が届いてから手順 2 へ進む。観測が止まったと返した plant と、報告を返さずに終わった plant は、返った理由と案内を言い換えずにレポートへ残し、残りの plant で進める — その plant の 0 件を「直すものが無い」の根拠にしない。4 本とも結果が無ければ、下の照合を済ませてから理由を報告して終える。

全部返ったら、許可 path を空として、控えた状態と同節の 2・3 で照合し、git から見えない書き先は控えた複写と比べ、「不在」と控えた file が現れていれば変わった path に数える。ただし `.claude/settings.local.json` の差 (「不在」から現れた場合を含む) が `permissions.allow` への entry の追加だけなら、変わった path に数えず、足された entry を手順 4 で人に示して残すか消すかを問う — 実行中の permission の確認に人が答えると Claude Code がここへ書くが、subagent が足した entry と中身からは見分けられない。変わった path が 1 本でもあれば手順 2 へ進まず、元に戻さずに次を人へ返して終える — 人が承認していない書き込みで、意図したものか事故かを判定できない。

- 変わった path の一覧 (逐語)
- 返った plant ごとのレポートの path
- 次に人が行う手順: 変わった path の差分を確かめ、残すか破棄するかを決めてから起動し直す

### 2. skill を監査し、本文を見直す

skill・MCP の存廃の返却から、次の 3 つの並びを作り、並びごとに上位の件数だけを開く (監査は読む transcript の数だけ subagent を起こすので、件数を絞る)。同数は skill 名の昇順にする。並びが空ならその並びは走らせず、レポートに「対象なし」と理由を書く。その plant の結果が無ければどの並びも走らせず、「対象を決められず」と理由を書く。

| 並び | 返却の項目 | 並べ方 | 件数 | 開く skill |
|---|---|---|---|---|
| 利用の多い skill | cwd の repo が追跡している skill の呼出数 | 呼出数が 3 回以上の skill を、呼出数の降順 | 2 | `skill-usage-audit` |
| 本文が変わった skill | 観測窓の中で本文が変わった skill | 変更の後の呼出数が 1 回以上の skill を、その数の降順 | 2 | `skill-usage-audit` (本文の差分を渡す) |
| 注入字数の多い skill | cwd の repo が追跡している skill の呼出数 | 本文の注入字数の合計が 1 字以上の skill を、合計の降順 (計測できなかった呼出しがある skill もその合計で並べ、レポートに下限と書く) | 1 | `compact-skill` |

監査の 2 つの並びの両方で開く件数に入った skill (2 つの返却の項目を SKILL.md の絶対 path で照らす) は、本文の差分を渡す 1 体で監査し、起動と件数を両方の並びに数える。「監査の対象外」と返れば、両方の並びが次の skill へ進む。本文の差分は、返却が「観測窓の中で本文が変わった skill」の行に添えた差分の file を渡す。

1 件につき 1 体を、手順 1 と同じ起動の仕方で、3 つの並びの分を同じ message に並べる。prompt は手順 1 の 1 文の SKILL.md を表の「開く skill」の `${CLAUDE_SKILL_DIR}/../<開く skill>/SKILL.md` にし、「cwd の repo の棚卸しを進め」を、監査なら「skill `<名前>` を監査し」、本文の差分を渡す監査なら「skill `<名前>` を、観測窓の中の本文の差分 `<差分の path>` を渡して監査し」、本文の見直しなら「`<SKILL.md の絶対 path>` の skill の本文を見直し」に替える (path は返却の項目が添えたもの。本文の見直しには、同名の skill を取り違えないよう名前でなく path を渡す)。「監査の対象外」か「見直しの対象外」と返った skill は対象に数えず、その並びの次の skill を起動する (起動は並びごとに件数の 2 倍までで、同じ skill を同じ skill で開き直さない。上限か並びの終わりに達したら、開けた件数のまま手順 3 へ進む)。「監査不能」か「見直し不能」と返った skill は 1 件に数え、起動し直さない。どれも理由をレポートへ残す。次の skill の起動は、先に起動した subagent が全部返って下の照合を済ませてから、同じ控え直しと照合を挟んで行う。返った報告は、反証の一次資料に使えるよう、監査は `<run-dir>/audit-<skill 名>.md`、本文の見直しは `<run-dir>/compact-<skill 名>.md` へそのまま書き出す。

監査と本文の見直しの subagent を起動する前に手順 1 と同じものを控え直し、全部返ったら同じ照合を行う。変わった path があれば手順 3 へ進まず、手順 1 と同じ 3 つを人へ返して終える。

### 3. 根本課題を挙げて反証を通す

層の定義と直す層の既定は、原則 leaf `${CLAUDE_SKILL_DIR}/../../knowledge/principle-index/references/leaves/principle-root-cause-and-hierarchy-of-controls.md` を Read して従う。

手順 1・2 の返却 (候補・反映しない候補・監査の最適化候補と構造の案) のうち、**合わせて 2 件以上を説明できる原因**を根本課題として挙げる。挙げるのは structures 層か mental models 層の原因だけにする。1 つの file の欠陥で説明できる原因は挙げず、候補のまま扱う — 1 件から仕組みを足すと、繰り返すかを確かめないまま仕組みが積まれる。次の 3 つの食い違いも根本課題に挙げず、その食い違いを直す候補を、どの根本課題にも束ねずに候補のまま手順 4 へ進める: 規範の本文が 2 か所にある・規範が要る場面に届いていない・常時に置く根拠の無い行が常時載っている。この 3 つは毎回の実行で見つかる原因なので、束ねると候補が反映されないまま起票だけが繰り返される。層ごとの材料は、events・patterns が各 plant の証拠、structures が harness の file、mental models が実行中 project の規範の返却にある前提。

根本課題 1 件は次を持つ。

- 層 (structures / mental models)
- 食い違い: 前提・構造・実際の動きのどれとどれが食い違っているか
- 説明するもの (候補と案の番号)
- 直す先
- 効いたかを確かめる観測 (直ったら消えるはずの繰り返し)

挙げた根本課題ごとに 1 体、`subagent_type: swat-skills:refuter` を同じ message に並べて起動する (`name`・`model`・`effort` は渡さない)。入力は根本課題ごとの file に書いて `<run-dir>` に置き、prompt にはその path 1 行だけを書く。file に書くのは次の 3 つで、挙げた経緯と推奨は書かない — 意図を渡すと、反証者は主張を補って読む。

- 指摘: 根本課題の食い違いの 1 文と、観点 (根本課題の層)、説明するとした候補の証拠 (plant のレポートの `file:line` と引用、候補の番号)
- 一次資料: plant のレポートと、直す先に挙げた harness の file の path (まだ無い file は書かない)
- 具体物として認めるもの: 説明するとした候補の証拠が主張と合わないこと、または主張する構造・前提が実在しないことを示す、レポートか harness の file の行

`refuted: true` で具体物が埋まった根本課題は崩れたものとし、理由と一緒にレポートに残して、束ねていた候補を束ねていない候補に戻す。残すのは `refuted: false` が返った根本課題だけにする。それ以外 (`入力を読めず:`・報告なし・具体物の無い `refuted: true` など) の根本課題は、反証を実施できなかったものとして人に示さない。名前が解決しないときは `general-purpose` で代えず、根本課題を 1 件も示さずに手順 4 へ進み、レポートに `反証 未実施: <error が挙げた available agents>` と書く — 反証を経ていない根本課題を示すと、証拠に無い原因が人の判断に混ざる。反証を実施できなかった根本課題は、層・食い違い・説明する候補と理由をレポートに残し、束ねた候補は上限から外れた根本課題に束ねた候補と同じに扱う。

残った根本課題を、説明する数の降順に並べ、上位 5 件までを人に示す (1 ラウンドで人が読める量に収める)。外れた分はレポートに載せる。

### 4. 1 ラウンドで人に示す

候補を次の 5 つに分ける。上から順に当て、最初に当たった行に決める。

| 分け方 | 当てる候補 | 扱い |
|---|---|---|
| 起票の設問 | 本文の見直しの返却と CLAUDE.md・rules の棚卸しの返却が「起票の設問」と付けた Computational 化の束 | 束ごとに 1 設問で問う (下の箇条)。根本課題が説明するものに挙がっていても、この行で扱う |
| 根本課題の中で示す | 人に示す根本課題が説明するもの (返却が反映しないとした候補と、監査の案を含む) | 根本課題の設問の中に並べる。根本課題の採否によらず反映しない — 症状だけを直すと、原因と証拠が残らない。次の実行で観測から再び候補になる |
| 反映しない | 返却が反映しないとした候補・編集できないとした候補・監査の最適化候補と、`write-for-harness` に渡す候補のうち、契約の「渡す args」が報告だけにするとしたパッチに当たる候補 | 手順 4 では示さず、レポートへ載せる。編集できない候補は、加えて手順 7 の報告で実 path と反映案を人に示す |
| 自律で直す種類 | 次の全部を満たす候補: どの根本課題にも束ねていない (上限から外れて示さない根本課題と、反証を実施できなかった根本課題に束ねた候補は束ねたものと数える) / CLAUDE.md・rules の棚卸しが返した / 手順 3 の 3 つの食い違いを直す候補ではない / 反映が 1 file の中の書き換え・統合・削除だけで、削除は、返却の「削除の根拠」が no-op か、環境を見れば分かる事実のものに限る / 反映先が実行中の repo の version 管理下にある (`git ls-files --error-unmatch <path>` が exit 0) | 一覧に 1 件 1 行で載せる |
| 人に問う | 残りの候補 (上限から外れて示さない根本課題と、反証を実施できなかった根本課題に束ねた候補を含む) | 1 件 1 設問で問う (手順 3 の 3 つの食い違いを直す候補を含む)。行を別の file へ移す候補は、下の箇条のとおり移動先の file ごとにまとめる |

条件は上の表のとおりに当て、「軽微か」を候補ごとに判断して一覧へ足さない。一覧の候補は、反映先が示す前に決まっていて、反映を version 管理で戻せる。

根本課題・人に問う候補・自律で直す種類の一覧を、次の形で **1 つの message** に載せ、人の応答を待つ。設問は「はい」で推奨を採れる文にする。AskUserQuestion は使わない — 5 つの plant の候補を合わせると、選択肢で問える量を超える。

```
❓ **Q1** - **<題>**: <根本課題なら層・食い違い・説明する候補・直す先・確かめる観測。候補なら対象・証拠・反映案・返却が挙げた選択肢。節を書き直す候補なら、返却が添えた前後の行の対応表と記号の差も>

➡️ 推奨: <採否と 1 句の理由>

---

**自律で直す一覧** (番号で外さなければ、趣旨を承認したものとして直します)

- A1 `<file>` — <bucket>: <変更の要旨>
```

- 並べる順は、根本課題 → 人に問う候補 (plant ごとに、返却の提示順) → Computational 化の束 → 一覧
- 前提の出所が推測の候補は、前提の文面を設問に載せ、採否と一緒に前提が合っているかを問う。人が直した前提を反映に使う
- 行を別の file へ移す候補 (返却の bucket が `move-to-path-scoped`・`move-to-doc`・`move-to-skill` のもの) は、移動先の file ごとに 1 設問にまとめ、移す行の一覧を設問に並べる。人は設問の中で行を番号で外せ、外された行は却下として扱う
- 手順 1・2 の照合で見つけた、実行中に足された allow の entry は、候補とは別の設問 1 つにまとめて示し、残すか消すかを問う。消すと答えた entry は手順 6 で本 skill が消す
- 設問が 1 つも無い実行でも、一覧を示して応答を 1 回待つ — 待たずに直すと、人が外す機会が無い
- 候補が多くても、本 skill は提示を打ち切らない。人が提示を打ち切ったら、答えの出ていない候補 (示して答えが無い候補と、まだ示していない候補) を `undecided` とし、一覧の候補も同じに扱って、それまでに承認された候補と採られた根本課題だけで手順 5 へ進む
- 答えから採否を 1 つに決められない設問は、その設問だけをもう一度示す。それでも決まらなければ `undecided` にする。「保留」と答えた候補も `undecided`
- 一覧から番号で外された候補は却下として扱う
- 「起票の設問」と付けた Computational 化の束は、束ごとに 1 設問で問い、移す対象の一覧を設問に並べる。人は設問の中で対象を番号で外せ、外された対象は却下として扱う。採られた束は手順 6 で反映せず、手順 5 で起票する
- 返却の選択肢のうち「issue 起票の提案で止める」を選んだ候補は `undecided (保留)` とし、反映せずに placement の候補と含意をレポートへ残す

### 5. 採られた根本課題と Computational 化の束を起票する

人が採った根本課題を、実行中 repo の issue の規範 (`docs/agents/issue-tracker.md` など) に従って 1 件ずつ起票する。本文には手順 3 の 5 項と、束ねた候補の証拠を載せる。置き場を決められない・tracker が拒むなどで起票が終わらなければ、根本課題をレポートに残し、止まった操作と理由を言い換えずに報告して、手順 6 へ進む。根本課題は harness にも他の文書にも反映しない。

人が採った Computational 化の束も、同じ規範に従って束ごとに 1 件起票する。本文は返却が添えた依頼文で、人が外した対象は除く。起票が終わらなければ、依頼文をレポートに残し、根本課題と同じに報告して手順 6 へ進む。

### 6. 承認された候補を反映する

反映するのは、人に問うて承認された候補と、一覧から外されなかった候補だけ。返却の「反映」欄が決める invoke の単位で進める (同じ file への候補を 1 回にまとめる返却がある)。

- 指示文の file (CLAUDE.md・rules・SKILL.md) と、返却の「反映」欄が component を宣言した file (move-to-doc の移動先の文書など) への反映は `Skill(swat-skills:write-for-harness)` に委ねる。後者の invoke では返却が挙げる component を同じ turn で宣言し、まだ無い文書は契約の `新規: <component> <目的>` で渡す。手順 1 で Read した契約 (`caller-contract.md`) が定める事項は契約に従う。invoke の直前に、候補の反映案と、返却が「添える制約」に挙げた文をそのまま宣言する。一覧から直す候補は、契約の `文面は承認済み` を宣言しない — 人は変更後の文面を読んでおらず、文面は書き手が規範に沿うよう直す
- invoke ごとに、契約の「委譲後の変更 path の照合」節の手順で照合する。許可 path は返却の「反映」欄が挙げた、その invoke の file 1 本 (契約に従って rules か文書の索引行を足す invoke では `CLAUDE.md`。「反映」欄が新しく作る file も挙げた invoke ではその file も)。返却が絶対 path で挙げた反映先は、契約のとおり repo root 相対に直して比べる。止めたときは、契約が残させるものをレポートと報告に残し、まだ渡していない候補も承認済み・未反映として手順 7 へ進む
- 文面の反映でないもの (settings の entry・skill の削除・人の側の操作) は `write-for-harness` に渡さず、返却の「反映」欄の手順のとおりにする。cwd の repo の中の file は本 skill が書く。書くのは返却の「反映」欄が挙げた file だけで、変更を手順 7 の全 diff に載せる (git の diff に出ない `.claude/settings.local.json` などは、書く前の複写との diff を載せる)。repo の外の file (`~/.claude/` 配下など) は書かず、人の側の操作として手順と反映案を示して受け渡す
- 同じ file への候補が別々の返却から来たとき (監査と本文の見直しが同じ SKILL.md を指したときなど) は、返却ごとの invoke の単位を保ったまま返却ごとに順に invoke する。先の invoke で文面が動くので、後の invoke には先の invoke の後の file を渡し、書き手が範囲を特定できずに書かなければ、契約の「反映を終えられなかったとき」の扱いに従う
- 返却の「反映」欄が反映の後の検証 (gate など) を挙げていれば、その invoke の照合の後に走らせる。通らなければ、結果を言い換えずにレポートと報告に残す
- 新しい rules の作成先か `paths:` の glob、索引行が指す文書の path か索引行が承認した候補に無ければ、契約のとおり invoke せずに no-placement とする。文書に書く invoke では、返却が挙げる component を同じ turn で宣言する
- 契約の「反映を終えられなかったとき」に当たった候補は承認済み・未反映とし、同節が載せさせるものをレポートと報告に残す。書かれた file は元に戻さない
- 全 invoke と書き込みが済んだら (照合で止めたときはそこまでで。反映が 0 件でも)、`${CLAUDE_SKILL_DIR}/../inventory-claude-md/SKILL.md` の手順 3 の項目 7「届き方の数」の、後の値を取る段落を Read し、それに従って CLAUDE.md・rules の plant のレポートの後の値を取る。起動する command と引数 (`--before` の observation JSON を含む) と前の値に使った `--covered` の file は、plant の返却が「後の値を取るのに要るもの」として挙げたものを使い、足した `--covered` の file は `<run-dir>` に書く。前の file の行は消さない。command を起動できないときは、後の値を「取れず」とし、止まった理由を言い換えずにレポートと報告に残す。plant の返却が無ければこの段は行わない

### 7. 報告する

次を人に示し、同じ内容を `<run-dir>/report.md` に書く。

1. **全 diff** と、候補ごとの戻す手順 — 候補の番号・変更した file・変更前と変更後の文面を並べる。人が番号で戻すよう求めたら、その候補の変更だけを元の文面に戻して diff を示す。続けて別立てで、invoke ごとの `write-for-harness` の返答のうち契約の「返答を呼び出し元の報告へ運ぶ」節が載せさせるものを載せる
2. **根本課題**: 示したもの (採否と、起票した issue か起票が止まった理由)・上限から外れたもの・反証で崩れたもの (理由つき)・反証を実施できなかったもの (層・食い違い・説明する候補・理由つき)
3. **候補の一覧**: plant × 番号 × bucket × 反映先 × 結果 (反映済み / 却下 / `undecided` / `undecided (保留)` / 反映しない / 編集できない / no-placement / 承認済み・未反映 / 起票済み / 起票が止まった)。`undecided` があれば件数と番号の一覧を表の下に 1 行書く。人が直した前提は、直した後の文面を候補の行に添える。結果が「編集できない」の行には、実 path と反映案を添える。返却が依頼文を添えた「反映しない」の行 (本文の見直しの分割) には、その依頼文を添えて人に提案する。Computational 化の束の行には、起票した issue か、起票が止まった理由と依頼文を添える
4. **plant ごとの状態**: 返ったレポートの path・観測の劣化・止まった plant の理由・手順 2 の並びごとに開いた skill (と対象から外れた skill、「対象なし」か「対象を決められず」の理由)・注入字数の多い skill の並びで計測できなかった呼出しがある skill の下限と計測できなかった数・本文の見直しの返却が「Computational 化の候補なし」と返した skill・本文の差分を渡した監査の逸脱の、「差分の中」「差分の外」「原因の行を特定できず」「変更の前の版」の印ごとの件数
5. **届き方の数** (CLAUDE.md・rules の plant): plant のレポートの項目 7 の前の値と、手順 6 で取った後の値を、同じ項目の 5 つの数ごとに並べる。0 を合格とする 4 つの数は、後の値で 0 でないものの該当の一覧を添える。常時載る量には合否を付けない。後の値を取れなかったときは、その理由を添える。plant の返却が無ければ「CLAUDE.md・rules の plant の結果なし」と書く

証拠 (session id・行番号・token の概算) はレポートにだけ置き、反映先の file には書かない。

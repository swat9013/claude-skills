# Fable 5.1 に向けて書くときの差分

対象モデルが Fable 5.1 (Mythos 5.1 を含む) のときに読む。**本 doc は差分層** — 文面規則の正本は [writing.md](../writing.md) で、ここは共通原則で足りない挙動差と、それに対応する公式サンプル prompt を判断の素材として引用形で残す層。共通原則を再掲しない。

Fable 5 系に共通する差分は [fable-5.md](fable-5.md) にあり、5.1 でもそのまま当たる。本書はその上に重なる 5.1 固有の差分だけを持つ。

## effort は選び直す

Fable 5 で effort を調整済みでも、段の名前は同じ思考量を指さないので選び直す。`medium` でおおむね Fable 5 並みの結果を低いコストで出す。

`xhigh` / `max` で長い成果物 (長文書の書き直し・大きな表・完全なコードファイル) を 1 回で頼むと、思考の中で下書きしてから本文で書き直し、待ち時間と出力が倍近くになる。まず `high` で回し、上げるのは効果を測れたときだけにする。

## 暗黙の並列 tool 呼び出しが減る

名指しされた複数の取得は並列に出すが、長いエージェントループで「次に要る独立した読み取り」が暗黙なだけのときは 1 turn 1 呼び出しに寄る。複数呼び出しの turn の比率を測り、低いときだけ次の 1 文を足す。置き場所は文言より効く — システムプロンプトではなく、tool 結果を返すたびにその user message の末尾へ新しいコピーを足し、過去のコピーは消さずに残す:

> First privately list what you need next; then request every item that doesn't depend on another's result in this one response.

## 途中経過は減る方向に振れる

Fable 5 より tool 呼び出し中のユーザー向け更新が少なく、effort が高く tool の連鎖が長いほど減る。コーディングの最終要約も短くなる。

1. **抑制系の指示を先に消す** — 「所見は最終応答まで溜める」「ナレーションしない」は更新が多すぎた旧モデル向けの指示で、5.1 では沈黙を招く
2. それでも足りなければ、ユーザー向けテキストが欲しいタイミングを書く:

> 始める前に、これからすることを 1 行で言う。作業中の短い更新はユーザーが追うのを助ける。最後は単独で読める短い振り返り (分かったこと・したこと・次) で締める。最後のメッセージだけを読む人にも全体が伝わるように。

ハーネスが tool の出力を畳む・隠すなら、そのことを伝える。伝えないと、ユーザーに「見せる」ためにコマンドを走らせることがある:

> そのコマンドの出力を見ているのはあなただけで、ユーザーの端末には数行しか出ない。ユーザーが読む必要のある部分は応答に書く。

## 文章が密になる

Fable 5 より 1 文が長く、段落の区切りが少なくなりやすい。飾った文体 (直接言えることを比喩や言い回しで置き換える書き方) を避けるべきものとして定義すると効く。短い形 (「飾った文体をすべて除く」) でも効くことが多い。文体の指示は、システムプロンプトよりセッション最初の user turn に置くほうが保たれる。

## 書式は控えめに振れる

旧モデルと逆に、太字・見出し・箇条書き・引用符が少なくなる。**書式を禁じる文面があれば消す**か、書式が適切な場面を言う規則に置き換える:

> 求められたとき、または内容が多面的で箇条書きが明瞭さを助けるときは、リストや箇条書きを使う。書式を最小にするよう明示的に求められたら、箇条書き・見出し・リスト・太字を使わない。会話的・個人的・感情的なやり取りでは平文で書く。

文書の要約では、出典の文を引用と示さずに写すことが Fable 5 より増える。正しい応答の完全な例を 1 つ (依頼・応答・なぜ正しいかの 1 文) システムプロンプトに置くと直る。

## 長い自律実行では 2 つの指示を組で置く

非同期の長い作業で「次に X します」と書いて止まる・依頼に含まれる手順の許可を求める、ことがある。[fable-5.md](fable-5.md) の「まれな停止」の自律指示に加えて、スコープを保つ指示を組で置く。自律指示の冒頭 (ユーザーは見ていない) は効いている部分なので削らない。止まってほしい確認があるなら、それを列挙する 1 文を足す:

> 依頼 (または承認された計画) がスコープを決め、スコープが成果物になる。黙って狭める・広げる・差し替えることをしない。定型的な判断は自分でし、読み方で成果物が大きく変わるときだけ確認する。途中で疑問が出たら、答えに依存しない作業を先に全部やり、置いた仮定を書く。一部が塞がったら、他の部分を完全にやり、何を残したかとその理由を正確に書く。決めた次の手順は実行するもので、宣言して turn を終えるものではない。依頼に要らない変更 (頼まれていない掃除・文書化・要らないファイルの変更) は最後に提案し、実施しない。


## 頼まれていない修正とテストを抜く

開放的な機能実装で、近くのコードの修正・追加のテスト・一時的な検査のテスト化まで入れることがある。何を入れないかを明示すると効く:

> 作業中に既存のバグ・性能の懸念・タスクが言及しない挙動を見つけても、要求された挙動がそれなしで動かない場合を除き、この変更で直さず、要約で follow-up として報告する。曖昧な点は文言と周辺コードが最も直接に支持する読み方で実装し、その仮定を要約に書く。検証の方法は自由で、一時的な検査は残さなくてよい。テストを commit するのは、タスクが求めたとき、またはこの repo がこの種の変更に既にテストを持つときだけにする。これは追加分の話で、タスクが求める挙動はすべて完全に実装する。

## low effort では記憶で答えやすい

`low` では検索・取得 tool を呼ぶ頻度が下がり、知っているつもりの名前 (製品・モデル・ツール) を古い知識で答える。その turn だけ effort を上げるのが最も簡単。文面で補うなら、名前を知っていることは現状を知っていることではないと書く:

> 自信を持って知っているとは言えない名前、または AI モデルや開発ツールのように数か月で状況が変わる分野の名前が中心の問いでは、その名前自体を確かめる対象として、答える前に検索し、少なくとも 1 つの検索語にユーザーが書いたとおりの名前を入れる。

## ファイル全体の書き直しを避けさせる

小さな変更でもファイル全体を書き直すことが Fable 5 より多い。

> 他の条件が同じなら、ファイル編集に使うトークンは少ないほうがよい。結果に影響しないなら、ファイル全体を書き直さず必要な箇所だけ編集する。

## 会話履歴は追記だけにする

turn ごとの注意書きを差し込んで次で消す・古い turn をその場で要約する・途中で system prompt を変える、は履歴の編集になり、thinking ブロックが無効になる (prompt cache も外れる)。turn ごとの注意書きは turn 限定の system message か tool 結果の後ろの text として追記し、過去のコピーは消さない。途中で指示や tool を変えるときは、`system` / `tools` を書き換えず会話途中の system message で足す。

## クライアント側で要約するなら残すものを明示する

会話をクライアント側で要約 (compaction) するなら、要約に残す項目を列挙すると効く — 起きた問題と対処、検討した案と退けた理由、決まったこと・合意・制約 (正確に)、現在地、未解決の事項、再構成しにくい具体 (名前・数値・日付・正確な文言)。要約のリクエストに tool 定義が載ったままなら、「この要約を書く間は tool を呼ばない」を必ず添える (添えないと要約の代わりに tool を呼ぶことがある)。

## refusal の誤検知を踏みやすい言い回し

分類器の誤検知は Fable 5 より減ったが、次の 3 つで起きやすい。コンパイル可否の問い方 (「エラーなくコンパイルできるか」ではなく「このプログラムにバグはあるか」と聞く)、知名度の低い言語 (言語の説明やドキュメントを文脈として渡す)、base64 のデータを context に返す tool (外す)。

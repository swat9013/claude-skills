# compact-skill

名指しした 1 skill の本文を、振る舞いを落とさずに短くする。下げるのは本文を読み込む token で、実行時の token (待ち合わせ・全量再走査など工程の消費) は扱わない。見直す skill の選定も扱わない — 選ぶ材料は `/skill-doctor` が示す skill ごとの利用量にある。

本文を一括で書き直させると、規範の知見が要約に潰れる。分類 → 候補 → 人間の承認 → 1 件ずつ反映、の順で進める。対象 file を書き換えるのは手順 6 の反映だけで、人間が承認していない write はゼロにする。変更の届け方は実行 project の運用に従う。

## 手順

### 1. 対象を決める

args の skill 名 (plugin prefix は外す) か path から、対象 skill の SKILL.md を解決する。args が無い・解決できないときは、見直す skill を人間に尋ねる。対象は編集権のある repo にある skill に限る — 上流から vendor した skill と、install 済み plugin の cache にある skill は、編集が上流に還らないので対象外と報告して終える。

見直す file は SKILL.md と、その skill の `references/` 配下の markdown 全部。各 file の文字数を `wc -m` で控える (手順 7 の合計差の起点)。本 skill の `wc -m` は手順 6 の前後差を含めてすべて UTF-8 の locale で取る — C locale では日本語 1 字が 3 と数えられ、前後で単位がずれる。

### 2. 診断表を読む

`${CLAUDE_SKILL_DIR}/../write-for-harness/references/patches.md` を Read する。パッチ 6 種の定義と編集してよい範囲・書き換えの粒度 (suite の有無の判定を含む)・診断表はこの file が正本で、手順 3 以降はこれを引いて使う。読めなければ分類に進まず、読めなかった path を報告して止まる — 正本なしに分類すると、どの規範で判断したかが誰にも見えない。

続けて、対象 skill に eval suite があるかを patches.md の判定で決める。書き換えの上限 (節単位まで / 項目単位まで) と手順 4 の確かめ方がこれで決まる。

### 3. 行・節ごとに分類して候補を作る

見直す file の全行・全節を診断表の「行の分類」へ当て、該当するパッチを候補にする。「残す」に当たる行も分類から外さない — 統合の要否を見るため。次の 2 種は全行で候補にする:

- **no-op** (現行モデルが既定でやることを言っているだけの行: 自己検証の指示・徹底化・強調語の盛りなど) は削除候補にし、手順 4 で確かめたものだけを承認に回す
- **禁止の形で書かれた規範**は、目標の行動を書いた肯定の形への書き換え候補にする。肯定の形で書けない hard guardrail は書き換えず、目標の行動と対になっていなければ対にする候補にする

候補 1 件ごとに、id・種別・対象 file・範囲 (先頭と末尾の文か節見出しで示す。行番号は反映の途中で動く)・現行の文面・変更後の文面 (削除なら無し)・当てた「行の分類」を書く。外出しには、新しく作る `references/` の file の path と移す範囲も書く。上限を超える書き換えは候補に出さず、上限に収まる単位へ割る。

patches.md が報告だけとするパッチ (「編集してよい範囲」と診断表で報告だけとされたもの) は、分割を除いて承認に回さず手順 7 の報告へ直接送る。分割は承認には回すが反映はしない — 候補に、切り出す範囲とその skill の leading word を書く。

### 4. no-op 候補を確かめる

no-op の削除候補は、その行を消しても挙動が変わらないと確かめたものだけを承認に回す。比べる版は対象 file を書き換えずに作る。

- **suite がある skill**: 対象 skill が属する plugin root ごとの使い捨てのコピーを作業ツリーの外に作り (suite・同梱の agent ごと)、そこで no-op 候補を全部消す。同じ suite を、eval の実行器に渡す plugin の path を現行の plugin root とコピーに替えて、同じ model で 1 回ずつ走らせる。走らせるのは skill を入れた状態だけにする (`claude plugin eval` なら `--ablation none`) — skill あり / なしを並べて走らせると、呼ぶべき側のトリガ判定が採点から外れる。各 case の score の差が、run ごとのばらつきの幅に収まれば全件を候補に残す。幅を超えた case があれば、no-op 候補を 1 件ずつ戻した版でその case を走らせ直し、差を消した候補 (= 差を生んでいた候補) を落とす。落とした後は、残した候補をまとめて消した版でもう 1 度走らせ、幅に収まることを確かめる (組み合わせで出る差は 1 件ずつ戻しても消えない)。それでも幅を超えたら、残した候補を全部未検証にする。suite を走らせられない環境でも、no-op 候補は全部未検証にする。未検証の候補は承認に回さず手順 7 で報告する
- **suite が無い skill**: 候補ごとに、Agent tool で subagent を 2 体同じ message で起動する (`model` 引数を渡さず、2 体を同じ model で走らせる)。1 体には行ありの本文を、もう 1 体には行なしの本文を prompt に埋め込んで渡し、その行が効くはずの場面の依頼を同じ文面で添えて、どう進めるかを答えさせる (tool で変更はさせない)。比べるのは、最初の行動・扱う範囲・止まるかどうかの 3 点で、言い回しの違いは差に数えない。3 点が同じなら候補に残し、違えば落とす

落とした候補は、違いの中身を添えて手順 7 で報告する。

### 5. 候補ごとに承認を取る

承認に回す候補を 1 件ずつ人間に示し、採否を決めてもらう。示すのは手順 3 で書いた候補の項目と、no-op なら手順 4 の結果。承認されなかった候補は反映しない。

### 6. 承認された候補を 1 件ずつ反映する

承認された候補 (分割を除く) 1 件につき 1 回、`Skill(swat-skills:write-for-harness)` を invoke する。最初の invoke の前に `${CLAUDE_SKILL_DIR}/../write-for-harness/references/caller-contract.md` (呼び出し元向けの契約) を 1 回 Read し、契約が定める事項は契約に従う。args の path は対象 file の絶対 path にする。外出しは外出し元の既存 file の path 1 本で 1 回 invoke する (委譲先が同じ invoke の中で対象 skill の `references/` に新しい file を作る)。1 件ずつにするのは、候補ごとの前後差と取りこぼしを人間が追えるようにするため。先に反映した候補で行が動くので、invoke の前に候補の範囲を手順 3 で書いた文面で特定し直す。invoke の直前に、次を宣言する:

- component は skill (`references/` の file を渡すときも同じ)
- 依頼はこの候補 1 件の反映で、変更後の文面は候補のとおり。外出しなら、新しく作る file の path と移す範囲
- no-op の削除なら、手順 4 で挙動が変わらないと確かめ済みであること (委譲先に確かめ直させない)
- 委譲先の findings と構造提案 (`structural_proposals`) は反映せず、報告に回す — 反映すると承認されていない文面が書き込まれる

invoke の前後で対象 file の `wc -m` を取る (外出しは新しい file の文字数も)。委譲先が反映を終えずに止まったら、その候補を承認済み・未反映として残し、委譲先が返した停止の理由と復旧の案内を報告に載せて次の候補へ進む。

### 7. 報告する

次を人間に示して終える:

1. 反映したパッチを 1 件 1 行で: 種別・対象 file・`wc -m` の前 → 後 (差)。続けて合計を SKILL.md と `references/` に分けて (手順 1 の値 → 最終)。外出しで新しく作った file も `references/` の合計に入れる — SKILL.md は skill を呼ぶたびに読まれ、`references/` は読む条件に当たったときだけ読まれるので、外出しは SKILL.md だけを減らす
2. 報告だけの候補と、委譲先の findings と構造提案
3. 手順 4 で落とした no-op 候補と違いの中身、および未検証の no-op 候補 (suite を走らせた結果を人間が渡せば、手順 4 から確かめ直せる)
4. 承認されなかった候補と、承認済み・未反映の候補

分割が承認されたら、切り出す範囲と leading word を書いた依頼文を作り、その依頼文で skill の新設を始めるよう人間に提案して止まる。新設の工程 (どの手順で作り、どこに置くか) は実行 project の運用に委ねる。依頼文には、新しい skill ができた後に元の skill から切り出した範囲を消す作業が残ることを書く (新設後に本 skill を対象 skill へもう一度当てると、既存 skill の呼び出しへの置き換えとして候補に出る)。

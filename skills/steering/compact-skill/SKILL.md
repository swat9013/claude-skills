# compact-skill

名指しした 1 skill の本文を、振る舞いを落とさずに短くする。機械が判定でき例外の無い規範と、入力から出力が一意に決まる手順は、本文が短くなるかによらず Computational 化の候補に挙げ、人が採ったものを起票する。下げるのは本文を読み込む token で、実行時の token (待ち合わせ・全量再走査など工程の消費) は扱わない。見直す skill の選定も扱わない — 選ぶのは呼び出し元 (skill を名指す人か、注入字数の合計で選ぶ統合の棚卸し) で、人が選ぶ材料は `/skill-doctor` が示す skill ごとの利用量にある。

本文を一括で書き直させると、規範の知見が要約に潰れる。分類 → 候補 → 人間の承認 → 1 件ずつ反映、の順で進める。Computational 化は反映せず、人が設問で採ったものだけを起票する。対象 file を書き換えるのは手順 5 の反映だけで、人間が承認していない write はゼロにする。変更の届け方は実行 project の運用に従う。

## 手順

### 1. 対象を決める

args の skill 名 (plugin prefix は外す) か path から、対象 skill の SKILL.md を解決する。args が無い・解決できないときは、見直す skill を人間に尋ねる。対象は編集権のある repo にある skill に限る — 上流から vendor した skill と、install 済み plugin の cache にある skill は、編集が上流に還らないので対象外と報告して終える。

見直す file は SKILL.md と、その skill の `references/` 配下の markdown 全部。各 file の文字数を `wc -m` で控える (手順 6 の合計差の起点)。本 skill の `wc -m` は手順 5 の前後差を含めてすべて UTF-8 の locale で取る — C locale では日本語 1 字が 3 と数えられ、前後で単位がずれる。

対象 skill の path に適用される設計 doc を、原則 leaf `${CLAUDE_SKILL_DIR}/../../knowledge/principle-index/references/leaves/principle-design-conformance.md` の「設計 doc の置き場の引き方」で決める。置き場の宣言は対象 skill の repo のものを読む。当たった設計 doc を Read し、保証・設計規則を手順 3 のために、path を手順 6 のために控える。当たる設計 doc が無ければ、手順 6 の報告に「設計 doc なし」と書く。

### 2. 診断表と行の種類を読む

次の 2 つを Read する。手順 3 以降はこれを引いて使う。

- `${CLAUDE_SKILL_DIR}/../write-for-harness/references/patches.md`: パッチ 7 種と診断表の正本
- `${CLAUDE_SKILL_DIR}/../write-for-harness/references/components/skill.md` の「本文の行の種類」: 行の種類の正本

どちらかを読めなければ分類に進まず、読めなかった path を報告して止まる — 正本なしに分類すると、どの規範で判断したかが誰にも見えない。

### 3. 行・節ごとに分類して候補を作る

見直す file の全行・全節を、診断表の「行の分類」と行の種類へ当て、該当するパッチを候補にする。「残す」に当たる行も分類から外さない — 統合の要否を見るため。次の 3 種は全行で候補にする:

- [**no-op**](../write-for-harness/references/patches.md#diag-no-op) (現行モデルが既定でやることを言っているだけの行: 自己検証の指示・徹底化・強調語の盛りなど) は削除候補にする。判定は診断表のその行に従う
- [**禁止の形で書かれた規範**](../write-for-harness/references/patches.md#diag-prohibition)は、目標の行動を書いた肯定の形への書き換え候補にする。肯定の形で書けない hard guardrail は書き換えず、目標の行動と対になっていなければ対にする候補にする
- [**機械が判定でき例外の無い規範と、入力から出力が一意に決まる手順**](../write-for-harness/references/patches.md#diag-computational)は、Computational 化の候補にする。本文が短くなるかと、移す値打ちがあるかでは絞らない — 実装されるまで字数は減らないので、短縮を物差しにすると 1 件も挙がらない。値打ちは人が決める

加えて、見直す file ごとに次の script を当て、当たった行を候補に挙げ、種別は診断表で決める。候補には、当たった語か文の長さを添える。

```bash
${CLAUDE_SKILL_DIR}/../write-for-harness/scripts/check-instruction-text.py lint <file>...
```

現行の本文が担う、手順 1 で控えた設計 doc の保証・設計規則のうち、変更後の本文に残らないものがある候補は、種別 (削除・書き換え・統合) を問わず振る舞いが変わる側に分類する。承認に回さず、担っていた保証・設計規則を添えて手順 6 の 3 で報告する — 本文から消すと、設計 doc が約束した振る舞いが黙って抜ける。

候補 1 件ごとに、id・種別・対象 file・範囲 (先頭と末尾の文か節見出しで示す。行番号は反映の途中で動く)・現行の文面・変更後の文面 (削除なら無し)・当てた「行の分類」を書く。外出しには、新しく作る `references/` の file の path と移す範囲も書く。項目単位の書き換え候補が同じ節に複数立つ節は、節を書き直す候補にしてよい。本文の全体を書き直す候補は出さず、節ごとの候補に分ける。節を書き直す候補は、patches.md の「書き換えの粒度」に従って作る (添える 2 つと、前にあって後に無い行の扱い)。記号の差は、現行の節と変更後の節を一時 file に書き、上の script を `diff <前> <後>` で呼んで出す。

patches.md が報告だけとするパッチ (「編集してよい範囲」と診断表で報告だけとされたもの) は、分割と Computational 化を除いて承認に回さず、手順 6 の報告へ直接送る。分割と Computational 化は承認には回すが反映はしない。分割の候補には切り出す範囲とその skill の trigger 語を、Computational 化の候補には移す対象と移し先 (既存の script の拡張・新しい script・lint・gate・hook) を書く。

### 4. 候補と設問ごとに承認を取る

承認に回す候補を 1 件ずつ人間に示し、採否を決めてもらう。示すのは手順 3 で書いた候補の項目。却下された候補は反映しない。Computational 化の候補は 1 件ずつ示さず、移し先ごとに 1 設問へ束ね、移す対象の一覧を並べて示す。人は設問の中で対象を番号で外せ、外された対象は却下として扱う。

採られた Computational 化の設問は、手順 5 の前に起票する。設問ごとに依頼文を 1 つ作り、対象 skill の repo の issue の規範 (`docs/agents/issue-tracker.md` など) に従って起票する。依頼文には移す対象 (人が外したものを除く) と移し先を書き、実装の後に元の行を消す作業が残ることも書く。新設と実装に使う手順 (どの skill・工程で作るか) は名指さず、実行 project の運用に委ねる。置き場を決められない・tracker が拒むなどで起票が終わらなければ、依頼文と、止まった操作と理由を言い換えずに手順 6 の 6 へ残して、手順 5 へ進む。
人が提示を打ち切ったら、答えの出ていない候補 (示して答えが無い候補と、まだ示していない候補) を `undecided` とし、承認された候補だけで手順 5 へ進む — `undecided` は却下された候補と分けて手順 6 の 4 に載せる。

### 5. 承認された候補を 1 件ずつ反映する

承認された候補 (分割と Computational 化を除く) 1 件につき 1 回、`Skill(swat-skills:write-for-harness)` を invoke する。最初の invoke の前に `${CLAUDE_SKILL_DIR}/../write-for-harness/references/caller-contract.md` (呼び出し元向けの契約) を 1 回 Read し、契約が定める事項は契約に従う。args の path は対象 file の絶対 path にする。外出しは外出し元の既存 file の path 1 本で 1 回 invoke する (委譲先が同じ invoke の中で対象 skill の `references/` に新しい file を作る)。1 件ずつにするのは、候補ごとの前後差と取りこぼしを人間が追えるようにするため。先に反映した候補で行が動くので、invoke の前に候補の範囲を手順 3 で書いた文面で特定し直す。invoke の直前に、次を宣言する:

- component は skill (`references/` の file を渡すときも同じ)
- 依頼はこの候補 1 件の反映で、変更後の文面は候補のとおり。外出しなら、新しく作る file の path と移す範囲
- 節の書き直しなら、skill の本文の見直しとして人が承認した節の書き直しであること
- `文面は承認済み` (契約の「検証の範囲」の宣言)
- 構造提案 (`structural_proposals`) は反映しないこと

委譲先が返した findings と構造提案は、反映すると承認されていない文面が書き込まれるので、どちらも手順 6 の 2 に回す。

invoke の前後で対象 file の `wc -m` を取る (外出しは新しい file の文字数も)。候補が契約の「反映を終えられなかったとき」の承認済み・未反映に当たったら、契約が呼び出し元の報告に載せさせるものを手順 6 の 4 に載せて次の候補へ進む (ただし下の照合で対象外の path が出たら、照合の止め方に従う)。

invoke ごとに、契約の「委譲後の変更 path の照合」節の手順で照合する。契約の照合の script の `--repo` には、対象 file の repo root (`git -C <対象 file の dir> rev-parse --show-toplevel` で引く。cwd の repo とは限らない) を渡す。許可 path は args の file 1 本で、外出しの候補では、invoke の直前に宣言した新しく作る file (対象 skill の `references/` の file) の path も許可する。止めたときは次の候補へ進まず、契約が残させるものを手順 6 の 4 に載せる。

### 6. 報告する

次を人間に示して終える:

1. 反映したパッチを 1 件 1 行で: 種別・対象 file・`wc -m` の前 → 後 (差)。続けて合計を SKILL.md と `references/` に分けて (手順 1 の値 → 最終)。外出しで新しく作った file も `references/` の合計に入れる — SKILL.md は skill を呼ぶたびに読まれ、`references/` は読む条件に当たったときだけ読まれるので、外出しは SKILL.md だけを減らす
2. 報告だけの候補。続けて別立てで、invoke ごとの委譲先の返答のうち契約の「返答を呼び出し元の報告へ運ぶ」節が載せさせるもの (委譲先の findings と構造提案を含む)
3. 手順 3 で、変更後の本文に設計 doc の保証・設計規則が残らないとして承認に回さなかった候補と、担っていた保証・設計規則
4. 却下された候補、承認済み・未反映の候補 (候補ごとに載せるものは手順 5 が決める)、`undecided` の候補 (件数と一覧を分けて)。script が挙げた候補は、件数と、そのうち却下された件数も書く
5. 照らした設計 doc の path (無ければ「設計 doc なし」の 1 行)
6. Computational 化の設問ごとの採否・外された対象と、起票した issue か、起票が止まった理由と依頼文 (候補が無ければ「Computational 化の候補なし」の 1 行)。Computational 化の設問と対象は 4 に載せず、ここにまとめる

分割が承認されたら、候補ごとに依頼文を作り、その依頼文で作業を始めるよう人間に提案して止まる。新設と実装の工程 (どの手順で作り、どこに置くか) は実行 project の運用に委ねる。依頼文には切り出す範囲と trigger 語を書く。新しい skill ができた後に、元の skill から切り出した範囲を消す作業が残ることも書く (新設後に本 skill を対象 skill へもう一度当てると、[既存 skill の呼び出しへの置き換え](../write-for-harness/references/patches.md#diag-existing-skill-copy)として候補に出る)

## 返却 (統合の棚卸しから開かれたとき)

`inventory-harness` の subagent として Read で開かれ、skill 名か SKILL.md の path を渡されたときは、人に問わず、file を書き換えない。手順 3 の一時 file は作業ツリーの外 (`/tmp` の下) に置く — 作業ツリーの中に作ると、呼び出し元の照合が変わった path に数えて棚卸しを止める。手順 1〜3 を進め、手順 4 以降は行わずに、最終報告で次を返す。

- 手順 1 で対象外に当たったら「見直しの対象外」と理由だけを返す。手順 1 が人間に尋ねるとした分岐に当たったときと、手順 2 で止まったときは、問わずに「見直し不能」と理由 (手順 2 なら読めなかった path) を言い換えずに返す
- 手順 1 で控えた file ごとの文字数と、照らした設計 doc の path (無ければ「設計 doc なし」の 1 行)
- 承認に回す候補 (分割と Computational 化を除く) の一覧。1 件ごとに: 手順 3 で書いた候補の項目 / 反映 (`write-for-harness` への候補 1 件ずつの invoke。args は対象 file の絶対 path で、component は skill。外出しは新しく作る file の path も許可 path に足す) / 添える制約 (手順 5 が invoke の直前に宣言するとした項目)
- 分割の候補は「反映しない」と付け、手順 6 の末尾の形で作った依頼文を文として添えて返す (人への提案と停止は呼び出し元が行う)
- Computational 化の候補は、移し先ごとに束ねて「起票の設問」と付け、束ごとに移す対象の一覧と、手順 4 の形で作った依頼文 (束の全対象を載せる。人が外した対象を除くのは呼び出し元) を添えて返す (人に問うことと起票は呼び出し元が行う)。候補が無ければ「Computational 化の候補なし」と返す
- 報告だけの候補と、手順 3 で設計 doc の保証・設計規則が残らないとした候補は「反映しない」と付けて返す。後者には担っていた保証・設計規則を添える
- script が挙げた候補の件数

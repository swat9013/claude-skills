# grill-with-docs

Skill tool で `swat-skills:grilling` と `swat-skills:domain-modeling` を呼び、両方の手順で対話を進める。用語の提案と用語集への採否は、domain-modeling の本文と用語集の書式より次節を優先する。

## 用語の見出し語は leading word から選ぶ

用語を新設・改名するときは、正準の語を提案する前に、その概念を一語で呼べる既存の語 (leading word — 業界・分野で広く通じる用語や設計パターン名のように、事前学習の知識に定着した語) を探す。leading word は一語で概念の知識を呼び出すので、会話・issue・コードで短く使い回せ、用語集を読んでいない agent にも意味が通る。

- 候補は grilling の設問で推奨の語として出す。複数あれば並べ、推奨を 1 つ選ぶ。例: 「支払いに失敗した契約へ催促を送り、間を置いて再請求する一連の流れ」は、作語の「再請求フロー」ではなく `dunning` と呼ぶ
- 当てはまるのは、既知の語の通常の意味が概念と一致し、用語集の既存の語とも衝突しないときに限る。ずれる語・衝突する語と退けた作語は、`_Avoid_` に理由付きで書く (例: `_Avoid_: 再請求フロー (作語), collection (債権回収と衝突)`)
- 表記は、その概念が多く書かれてきた言語に合わせる。英語起源の技術用語は原語で置き、会話の初出に日本語を添える (用語集の項では定義文がこれを兼ねる)。日英どちらにも定着した語は原語に倒す。日本語にしか無い概念は日本語で置く。定着していないカタカナの音訳は、概念の知識を呼び出さないので使わない
- 既知の語を選んでも、この project でその意味を絞るなら用語集に項を立てる — 用語集の書式が除く General programming concepts は、project での絞りが無い語だけを指す

当てはまる既存の語が無いときに限り、project で語を作る。作ったことを設問で user に告げる。作った語は事前学習の知識を呼び出せないので、項の定義だけで意味が通るように書き、他の文書では定義を言い換えずに項を参照する。語は、概念が何であるかを言い当てる語にする (`Manager`・`handle`・`data` のように中身を語らない汎用語は、名前が約束する意味を持たない)。

## 決まった判断を規範へ codify する

判断が決まるたびに、その判断を codify できるかを判定する。codify とは、人の決定を、次に同じ種類の判断が来たとき agent が自分で下せる規範 (CLAUDE.md・rules・skill の指示文・ADR など、agent が次の判断で読むもの) へ書き起こすこと — 計画や issue に書いた決定はその 1 件にしか効かず、同じ種類の判断が次も人に回る。本節は backlog-triage skill と、深掘り待ちの issue に投稿された手順コメントに従って issue を深掘りする別セッションからも Read されるので、問い詰めの外でも通る手順として書く。Read で開いて本文の path に展開されていない変数が残っていれば、その変数を本 file のディレクトリと読み替える。

- 判断を「どんな場面で・どう決める」の 1 本の規則に言い直せ、その件固有の事実に頼らず、既存の規範がまだ決めていないか決めた内容と食い違うなら codify できる
- user が agent の推奨や、agent が自律で下して記録した判断 (CL の説明文などに残したもの) を覆したときも、その判断を導いた規範を同じ判定にかけ、規範を直す文案を出す — 規範を直さないと、同じ種類の判断で同じ誤りが繰り返される
- codify できるなら、書き込む先と規範の文案を、その判断を問う設問に推奨と並べて逐語で出す — user が読んでいない文面を規範に書かない。規則は指示文 (その領域を既に扱う file があればその file、無ければ新しい file) に書く。ADR にするのは、戻しにくく・文脈なしでは意外で・実際の代替案から選んだ決定だけにする
- 承認された文案は、その規範を引く issue 本文の書き換えより先に反映する — 反映できなかった規範を本文が引くと、実在しない規範を指す参照が残る。問い詰めの中では、その設問で承認された時点で反映する (用語集の更新と同じ)。指示文は `${CLAUDE_SKILL_DIR}/../../steering/write-for-harness/references/caller-contract.md` を Read し、その契約に従って `swat-skills:write-for-harness` を Skill tool で invoke する。ADR は write-for-harness が扱わないので、対象 repo の ADR の規約に従って書く (問い詰めの中なら domain-modeling の ADR の手順)。反映できなかったら、その規範を引く issue 本文の書き換えと label の変更を保留し、止まった操作と理由を user へ伝える (write-for-harness が止まったときに伝えるものは契約に従う)
- 対象が issue なら、本文には決定を書き直さず、codify した規範の path と見出しを引く。本文に書き換える箇所が他に無くても、引く 1 行を足す書き換えにする
- 終わりに、反映した規範の path とそれを引く issue を挙げ、規範が既定 branch に届くまでその issue を実装する側からは規範が読めないことを user へ伝える

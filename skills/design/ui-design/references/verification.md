# UI 設計の検証

設計 doc は書いた時点では仮説にすぎない。実装前に 3 段で検証する。段 1・段 2 は必須、段 3 は `navigation.puml` を持つ設計で必須。

## 段 1: 操作シナリオ (必須)

具体的な操作の並びを **2〜3 本**手書きし、成果物一式が矛盾なく表現できることを確かめる。README.md の「操作シナリオ」節に置く。

書き方:

- 代表的な流れを選ぶ。正常系 1 本 + 設計判断が効く異常系 1〜2 本 (入力エラーからの復帰・権限で入口が分岐する・途中離脱と再開)
- 各ステップは「どの画面で・何を操作し・どの画面へ移り・何が変わるか」で書く。画面 ID と component 名を具体的に出す (抽象名のままだと state の漏れが見えない)
- **検査するのは機械検査 (段 2・段 3) が見ない側**: 情報要素の出どころ (画面に出す情報が、そこへ来るまでの遷移で確定しているか) / 中断と再開 (途中離脱して戻ったとき、どの画面のどの state に戻るか) / 権限差 (同じ画面でも見えるものが変わる場合の表現)
- 末尾に検証の結論を 1 行書く (「N シナリオとも矛盾なく表現できる」/ 表現できなかった点と直した設計)

**シナリオが表現できなかったら設計側を直す。** シナリオを曲げて通すと、実装時に同じ矛盾へ戻ってくる。

`sud-design` のユースケースとは別物として書く: ユースケースはアクターの**意図**をステップにする規約 (画面に触れない) で、操作シナリオは逆に具体的な画面と操作で設計を検査する装置。

## 段 2: 成果物間の相互参照 (必須)

画面・component・トークンは 3 つの file に分かれて書かれるので、片方だけ直して他方が取り残される壊れ方をする。同梱 script が相互参照を機械検査する:

```bash
uv run ${CLAUDE_SKILL_DIR}/scripts/check-ui-design.py docs/design/<name>/
```

検査する内容 (詳細と exit code は script の `--help` が正本):

| # | 検査 | 典型的な壊れ方 |
|---|---|---|
| 1 | 画面 ⇔ 遷移 | `screens.md` に足した画面を `navigation.puml` に足し忘れる / 遷移図にだけ画面が残る |
| 2 | component ⇔ 画面 | 画面を消したのに component の出現画面列に ID が残る |
| 3 | state 網羅 | `Button` を名乗る component に `loading` を書き忘れる |
| 4 | token 未定義参照 | `screens.md` が `` `--accent` `` を名指すが `tokens.md` に無い |
| 5 | 省略の宣言 | 成果物を省いたのに README に理由 1 行を残していない |

**exit 1 の出力は違反を名指しする。直すのは設計 doc の側**で、検査を回避するために表から行を消さない。

## 段 3: 画面遷移の網羅検査 (`navigation.puml` を持つ設計で必須)

未定義の 画面×操作 は、図の見た目からは「描き忘れ」と「設計判断としての未定義」が区別できない。`sud-design` と同じ script を共有して検査する:

```bash
uv run ${CLAUDE_SKILL_DIR}/../sud-design/scripts/check-statechart.py docs/design/<name>/navigation.puml
```

- exit 0 = 全組合せが「遷移あり」か「理由つき uncovered 宣言」で説明されている
- exit 1 の出力は組合せを名指しする。**定義漏れなら遷移を足し、意図した未定義なら `' uncovered: <画面> x <操作> — <理由>` を navigation.puml に足す**。理由を書けない組合せは定義漏れの側
- 到達不能画面 (入口からたどり着けない画面) と初期遷移の欠落も同時に検査される
- 宣言が残骸化した場合 (遷移を後から足した・画面を改名した) も同じ script が落とすので、遷移を変えたら再実行する

script は `sud-design` の持ち物で、記法の正本も向こう側にある。**複製しない** — 複製すると記法の仕様が 2 箇所へ分岐する。

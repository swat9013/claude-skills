# goal-drive

このセッション (goal を進めるセッション) は、人と goal 契約を合意し、goal が引く issue を実装へ進め、人の判断が要る問いを判断待ちに積み、受け入れ条件ごとの証拠をそろえて人の受け入れを待つ。次の 3 つを別のものとして扱う: 作業が実行された (実装役の報告) / 検査が通った (検査・レビュー・CL の merge) / 人が結果を受け入れた。前の 2 つは受け入れの証拠で、goal を終えるのは人の受け入れの言葉だけにする。

このセッションが持たないもの: issue 1 件の実装と CL 計画の中身 (手順 3 が Read する手順が持つ)、triage の裁き、merge するかの判断 (人が決める)。

## 守ること

- **契約は合意で固定する。** 合意した goal 契約はどの欄も書き換えない。欄を変える求め (範囲を狭める・受け入れ条件を直す) が出たら、人が今の goal を取り下げ、新しい goal を手順 2 から始める
- **人の言葉を作らない。** 合意・判断待ちへの答え・受け入れ・差し戻し・取り下げは、人が言った言葉を逐語で記録に書く。記録に無いものを、あったものとして扱わない
- **issue と CL の状態を記録に写さない。** 要るたびに tracker から引く — 写しを持つと、記録と tracker のどちらが正しいかを毎回確かめることになる
- **人との長い対話をこのセッションで行わない。** 深掘り・設計を詰める対話・判断待ちへの答えは別の pane のセッションで行い、このセッションが受け取るのは決定だけにする — 対話の全文がここに積もると、割り当てと中継に使える文脈が減る
- **問いを積んでも、関係の無い作業を止めない。** 答えを待つのは、その答えに依存する作業だけにする

## goal の記録

goal 1 つにつき file を 1 つ、`~/.local/state/swat-skills/goals/<repo の語>/<goal の識別子>.md` に置く。`<repo の語>` は CL 置き場 (cwd の repo) の `<owner>/<repo>` の `/` を `-` に替えたもので、remote が無ければ repo の root のディレクトリ名にする。識別子は `<合意前の記録を作った日付>-<結果を表す短い ASCII の語>`。同じ名前の記録が既にあれば、末尾に `-2` から順に番号を足す (手順 4 の名前の script も、この形の識別子を読む) — 同じ path へ書くと、前の goal の合意と経過が消える。書き手はこのセッションだけにし、`~` を home の絶対 path に展開して Write と Edit で書く — Bash の sandbox は repo の外への書き込みを拒むことがある。

記録は次の節を持つ。節に無い情報 (issue の状態・CL の状態・対話の経過) は書かない。

| 節 | 中身 |
|---|---|
| 状態 | 合意前 / 進行中 / 受け入れ待ち / 受け入れ済み / 取り下げ のどれか 1 つ |
| 置き場 | issue 置き場と CL 置き場 |
| 契約 | 結果と理由・観測できる受け入れ条件・不変条件・範囲外の 4 欄 |
| 合意 | 人の合意の言葉 (逐語) と時刻 |
| issue | goal が引く issue の ID。足し引きは「経過」に理由と一緒に残す |
| 判断待ち | 問いごとに: 番号 (`Q<n>`)・問い・選択肢と推奨・問いを上げた作業・積んだ時刻・人の答え (逐語) |
| 証拠 | 受け入れ条件ごとに: 確かめた issue か CL の ID・確かめた時刻・観測した事実 (実行したコマンドと結果、見た commit を含む) |
| 受け入れ | 人の受け入れか差し戻しの言葉 (逐語)・時刻・差し戻しの理由 |
| 経過 | 起きたことの追記の列 (時刻つき。書き換えず足す)。開いた対話の pane の `pane_id` と名前、起動した CL エージェントの行の名前・branch・worktree の path・`deps`・`merge_in` もここに書く |

## 手元の既定 branch を進める

対象 repo の手元の既定 branch を、CL 置き場の remote の既定 branch の先頭へ進める。進めるのは、対話の pane を開く前 (手順 4 の 1) と、merged の CL が増えたのを見たとき (手順 3 の読み替え) にする。対話のセッションは手元の checkout から規範と設計 doc を読むので、merge のたびに手元が遅れると、深掘り・設計を詰める対話・判断待ちへの答えが古い版の上で決まる。

1. 対象 repo で `git fetch <remote>` を呼ぶ。`<remote>` は CL 置き場を指す remote、`<既定 branch>` は `git symbolic-ref --short refs/remotes/<remote>/HEAD` の出力から `<remote>/` を除いた名前 (この ref が無ければ、`git remote set-head <remote> --auto` で作ってから引き直す)
2. `git worktree list` で既定 branch を checkout している作業ツリーを引く。あれば `git -C <その作業ツリー> merge --ff-only <remote>/<既定 branch>` で、無ければ `git fetch <remote> <既定 branch>:<既定 branch>` で進める。どちらも fast-forward でしか進まないので、merge commit を作らない
3. どれかのコマンドが失敗したとき、`git rev-parse <既定 branch>` と `git rev-parse <remote>/<既定 branch>` が違う commit を指すとき、または手順 4 の 1 で `--cwd` に渡す checkout が既定 branch の上にないときは、失敗したコマンドか食い違った値を「経過」に書いて人に伝え、そのまま作業を続ける。進められないのは、未 commit の変更が取り込む変更と重なる・手元の既定 branch が分岐しているか remote より先にあるときなど。これらは人の作業の途中で正常に起き、止めると関係の無い作業まで止まる

## 手順

turn を終えるのは、人の言葉を待つとき、実装役・triage・別の pane からの知らせを待つときだけにする。途中の報告は、次の tool 呼び出しと同じメッセージに書く。

1. **herdr を確かめ、goal を決める。** `herdr pane current` を呼ぶ。失敗したら、出力で分けて案内して止まる — 別の pane を開けないと、対話がこのセッションに積もる。コマンドが見つからなければ <https://herdr.dev> からの導入、herdr の pane の外なら pane の中での起動し直し、socket への接続の失敗なら sandbox から herdr を除外する設定 (`/swat-skills:setup` が提案する) を案内する。成功したら、出力の `pane_id` を使い、「経過」に書く。会話の圧縮や再開の後は呼び直して得る。得た値が「経過」の値と違えば、開いている対話の pane を `herdr pane close` で閉じ、答えの無い問いを手順 4 で渡し直す — 開いている対話のセッションは古い `pane_id` へ知らせを送る。別の pane のセッションは、この `pane_id` 宛にこのセッションへ知らせを送る — 端末のタイトル (`terminal_title_stripped`) はセッションが扱う話題に合わせて書き換わるので、宛先に使うと知らせが届かなくなる。`pane_id` は書き換わらない。herdr のコマンドは 1 つずつ単文で呼ぶ — 複合コマンドにすると sandbox の除外に当たらず、socket に繋がらないことがある。

   args と同じ名前の記録があれば、その goal を続ける (手順 6 の「止まった goal を続けるとき」)。無ければ args を達したい結果として読み、手順 2 へ進む。ただし args が識別子の形 (日付で始まる ASCII の語) なのに記録が無ければ、新しく始めず、cwd の repo が合っているかを人に確かめる。args が無ければ、対象 repo の記録のうち状態が受け入れ済みでも取り下げでもないものと、受け入れ済みで merge への追従を終えたと「経過」に書いていないものを挙げ、続けるか新しく始めるかを人に問う。挙げる記録が無ければ、達したい結果を人に問う。

2. **goal 契約を合意する。** 関わる issue を tracker から読む。issue 置き場の決め方と issue の引き方は、`${CLAUDE_SKILL_DIR}/../stacked-implement/SKILL.md` の「入力を読む」の手順に従う (その手順の `${CLAUDE_SKILL_DIR}` は `${CLAUDE_SKILL_DIR}/../stacked-implement` と読む)。CL 置き場は cwd の repo とする。契約の 4 欄の案を作り、状態を合意前にして記録を書き、案を人に示す。まだ issue になっていない作業があれば、起票する作業の一覧を案に添える。
   - 受け入れ条件は、誰が何を見れば満たしたと言えるかを書く。issue ごとの受け入れ条件の写しにせず、複数の issue をまたぐ結果を書く — issue の検査はその issue の範囲しか見ない
   - goal が引く issue の集合は契約に入れない (合意の後も足し引きする)

   人が直しを求めたら案を直して示し直す。人が合意すると言ったら、その言葉を「合意」に逐語で書き、状態を進行中にする。合意の言葉が無い間は、作業を割り当てず、起票もしない。合意の後に、添えた一覧の作業を対象 repo の issue の規範に従って起票し、goal に足す。

3. **issue を進める。** goal が引く issue の状態を tracker から引き、状態ごとに次へ回す。
   - **`ready-for-agent`**: `${CLAUDE_SKILL_DIR}/../stacked-implement/SKILL.md` を Read し (会話の圧縮や再開の後は読み直す)、その親セッションとして同書の手順を先頭から末尾まで通して実装へ進める。名指しの集合は、この状態の issue のうち、issue を閉じる CL が open でも merged でもないものとする。CL 計画が動いている間にこの状態に着いた issue は、同書の「計画の修正」として足す。同書は次の読み替えだけを当てて通す。手順 6 から同書の「merge に追従する」だけを通すときも、この読み替えをすべて当てる
     - CL エージェントを起動するたびに、行の名前・branch・worktree の path と、同書の計画の記録のその行の `deps` と `merge_in` を「経過」に書く。同書の計画の修正で起動済みの行の `deps` か `merge_in` を直したら、直した後の値も書く
     - 同書と、同書が Read させる同書の `references/` の本文にある `${CLAUDE_SKILL_DIR}` は、`${CLAUDE_SKILL_DIR}/../stacked-implement` と読む — Read で開いた本文では展開されず、そのまま読むとこの skill のディレクトリを指す
     - 同書と、同書が Read させる同書の `references/` がユーザーに問うとする箇所 (AskUserQuestion を含む) は、その場で問わず、手順 4 で判断待ちに積む。答えに依存しない行は進める
     - 同書の最終報告が `見送り` なら (同書の「計画の修正」で外した行の `見送り` を除く)、その行が持つ issue をすべて名指しの集合から外し、理由を添えて手順 4 で判断待ちに積む (選択肢: 見送る / 人が障害を除いてからやり直す)。人の答えが届くまで起動し直さない
     - `ready-for-agent` になった follow-up issue は、結果に関わるなら goal に足して「issue」と「経過」に書く。契約は書き換えない
     - 同書の「完了報告」まで進んだら、報告を人に示したうえで手順 5 へ進む。同書の「merge に追従する」は、人が merge するたびに同書のとおり続ける
     - 同書の「merge に追従する」で merged の CL が増えたのを見たら、「手元の既定 branch を進める」を行う
   - **`needs-grilling` に当たる label** と、triage が深掘りを要ると返した issue: 手順 4 の別の pane で深掘りする。決定が本文に書かれて `needs-triage` に着いたら、次項へ回す
   - **`needs-triage`** と、状態の label が無い issue: 同書の「起票された follow-up issue」の項と同じ形で、triage の subagent に渡す。返った状態で、この手順をもう一度当てる
   - **`needs-info`・`ready-for-human`・`wontfix` の issue と、`tracking-issue` に当たる label の issue**: 人に要ること (見送るかを含む) を問いにして、手順 4 で判断待ちに積む
   - **closed の issue と、見送ると人が決めた issue**: 進めない。見送りは理由を「経過」に書く

4. **判断待ちに積み、別の pane で人と決める。** 問いを「判断待ち」に書く (問い・選択肢と推奨・問いを上げた作業)。問いに答える pane は同時に 1 つにし、答えの無い問いをまとめて渡す。pane が開いている間に積んだ問いは、その pane を閉じた後に次の pane で渡す。深掘りと設計を詰める対話は 1 件につき 1 つの pane にし、問いと混ぜない。
   1. pane を開く: 先に「手元の既定 branch を進める」を行う (進められなくても、その節の 3 のとおり pane を開く)。続けて `herdr pane split --pane <手順 1 の pane_id> --direction right --cwd <対象 repo の絶対 path> --no-focus`。出力の `pane_id` を「経過」に書く。`--current` は使わない — 人が focus している pane に解決し、別の場所に開く
   2. セッションを起動する: `herdr agent start <名前> --kind claude --pane <pane_id> -- --name <名前> --model fable --effort low`。名前は `${CLAUDE_SKILL_DIR}/scripts/dialog-name.sh <goal の識別子> <n>` の出力をそのまま使う (`<n>` は「経過」に書いた対話の pane の数で、今開いた pane を含む)。字数は数えない — herdr は小文字で始まる 32 字以内でない名前を `invalid_agent_name` で拒み、script はその形に収めて出す。`--model` と `--effort` を外すと、利用者の既定の model と effort で立ち上がる
   3. 依頼を送る: `herdr agent prompt <名前> '<依頼文>'`。依頼文は 1 つの引数で渡し、文中の `'` は `'\''` と書き、目印の `[依頼 <名前>]` を 1 行目の先頭 (深掘りと設計を詰める対話では slash command の次の行の先頭) に置く — slash command は入力の先頭に無いと起動しない。`--wait` は付けない — 人との対話が終わるまで戻らず、中継が止まる。送った後に `herdr agent read <名前> --source recent-unwrapped --lines 30` で画面を読み、目印の `[依頼 <名前>]` が出ていなければ 1 回だけ送り直し、送り直しても出なければ下のコマンドの失敗と同じく扱う — 起動の直後の送信は、成功を返しても届かないことがあり、`agent_status` では見分けられない。長い依頼文は画面で折りたたまれて冒頭の文と照らせなくなるので、照らすのは折りたたみでも折り返しでも切れない短い目印にする
   4. 人に知らせる: `herdr notification show '<goal の識別子>: 判断待ち' --body '<問いの数と pane の名前>' --sound request`

   どれかのコマンドが失敗したら、失敗したコマンドと出力を「経過」に書き、人に伝える。その問いに依存する作業だけを待たせ、ほかは進める。

   依頼文は用途で分ける。どれにも、終えたら Bash で `herdr agent prompt <手順 1 の pane_id> '[<対話セッションの名前> からの知らせ] <知らせ>'` を単独のコマンドで 1 回実行して知らせを送ることを、理由 (複合コマンドにすると sandbox の除外に当たらず送れない) と一緒に書く (文中の `'` は `'\''` と書く)。このコマンドが失敗したら、知らせの全文を人に示し、それを goal を進めるセッションに伝えるよう頼むことも書く。
   - **深掘り**: 依頼文は `/swat-skills:grill-with-docs <issue 置き場>#<N>` で始め、続けて上の知らせの指示を書く。知らせは `深掘り済み <issue 置き場>#<N>` とする
   - **設計を詰める対話**: 設計 doc の文面を決める問い (stacked-implement の「設計 doc の直しを問う質問」の項が人に頼む設計の詰めを含む) は、問いへの答えに混ぜずに渡す。依頼文は `/swat-skills:grill-with-docs` で始め、続けて問い・選択肢と推奨・文脈を読める先と上の知らせの指示を書く。決めた設計 doc の直しを、stacked-implement の同じ項が頼む形の CL として出すよう頼む。依頼文には問いを上げた行の issue の参照を `Refs <issue 置き場>#<N>` の解決した文字列で入れ、CL の説明文にそのまま書かせる。issue の本文の扱いは問いへの答えと同じにする。知らせは、`答え Q<n>:` で始めて人の承認の言葉の逐語を続け、最後の行を `設計 doc の CL <参照>` とした 1 通とする。答えの逐語は「判断待ち」に書き、参照は待たせた行の名前と並べて「経過」に書き、同じ項のとおり計画の記録にも書く
   - **問いへの答え**: 依頼文には、問いごとに番号・問い・選択肢と推奨・文脈を読める先 (issue と CL の参照) を書き、人と対話して全部の問いの答えを決めるよう頼む。issue の実装に効く答えは、`swat-skills:issue-tracker-operations` の本文の書き換えの手順で、その issue の本文に書かせる。CL エージェントを起動済みの issue (「経過」に起動の行がある) と、issue を閉じる open の CL がある issue の本文は書き換えさせない — 書き換えると状態の label が動き、実装中の issue がもう一度割り当てられる。知らせは、問いごとに `答え Q<n>:` で始め、答えを決めた人の言葉の逐語 (複数行でもよい) を続けた 1 通とする — 要約を受け取ると、人が言っていない文を人の答えとして記録に書くことになる

   知らせは人の入力と同じ形で届くので、先頭が `[<対話セッションの名前> からの知らせ]` の入力を知らせとして読み、その中の `答え Q<n>:` に続く文を人の答えの逐語とする。知らせが届いたら、人の答えを「判断待ち」に書き、問いを上げた作業 (CL エージェントなら SendMessage) へ答えを渡す。人が承認した文面の添え方と、答えを受けた後の続きは、問いを積んだ stacked-implement の項に従う。その pane に渡した問いが全部答えられたら (深掘りと設計を詰める対話なら知らせが届いたら)、`herdr pane close <pane_id>` で閉じる。深掘りの決定は issue の本文から読む。

   知らせを受けて turn を始めるたびに、開いている pane のセッションが残っているかを `herdr agent get <名前>` で確かめる。消えていれば、答えの無い問いを次の pane で渡し直す。人が「答えた」と言ったのに知らせが届いていなければ、issue の本文を読み、本文に無い答えは人に 1 行で言い直してもらって書き、届かなかったことを「経過」に残す。

5. **証拠をそろえる。** goal が引く issue がどれも、closed か、issue を閉じる CL が ready で出ているか、見送った理由が「経過」にある状態になったら、受け入れ条件を 1 つずつ確かめ、「証拠」に書く。実装役の報告を観測の代わりにしない。満たさない条件があれば、足りない作業を対象 repo の issue の規範に従って起票して goal に足すか、直しを依頼して、手順 3 へ戻る。全部の条件に証拠がそろったら、状態を受け入れ待ちにし、条件ごとの証拠と、見送った issue と理由を人に示して、「goal を受け入れる」か「差し戻す」の語で答えるよう求める。この問いには受け入れと差し戻しの 2 つだけを置き、記号や番号を振った打ち手の選択肢を並べない — 作業を足して続ける案は差し戻しの中身なので、示すなら差し戻したときに起票する案として、「受け入れる」の語を使わずに添える。打ち手の選択肢と並べると、選択肢を選んだ答えを受け入れと取り違える。

6. **人の受け入れを受ける。続きから進める。** 人の言葉を「受け入れ」に書く前に、その言葉が手順 5 の問いへの答えで、goal の結果を受け入れるか差し戻すかのどちらかとしか読めないことを確かめる。手順 5 の問いへの答えでない言葉 (別の問いへの答えなど) は、受け入れにも差し戻しにも数えない。記号・番号・「はい」のような短い答えと、受け入れる対象が goal の結果以外 (提案など) とも読める言葉は、記録せず、状態も変えずに、「goal を受け入れる」か「差し戻す」の語で言い直してもらう。
   - 人が受け入れると言ったら、その言葉を「受け入れ」に逐語で書き、状態を受け入れ済みにする。open の CL が残っていれば、同書の「merge に追従する」だけを、全部の CL が merged か closed になるまで続け、終えたことを「経過」に書いて終える。この間に `ready-for-agent` になった follow-up issue は goal に足さず、人に知らせるだけにする。CL が全部 merge されていても、検査が全部通っていても、この言葉が無ければ受け入れ済みにしない
   - 人が差し戻したら、理由を「受け入れ」に書き、状態を進行中に戻す。差し戻しがどの issue も指さなければ、足りない作業を対象 repo の issue の規範に従って起票して goal に足す。手順 3 へ戻る
   - 人が取り下げると言ったら、その言葉を「経過」に書き、状態を取り下げにする。開いている対話の pane を閉じる。動いている CL エージェントがあれば、止めるか、新しい goal で続けるかを人に問う。止めるときの未 commit の変更・push 済みの branch・出した CL の扱いは、`${CLAUDE_SKILL_DIR}/../stacked-implement/SKILL.md` の「計画の修正」で行を外すときに従う
   - 止まった goal を続けるときは、記録を読み、issue と CL の状態を tracker から引き直す。記録の状態が合意前なら手順 2、進行中なら手順 3、受け入れ待ちならこの手順の先頭から進める。受け入れ済みで open の CL が残っていれば、同書の「merge に追従する」だけを続ける。答えの無い判断待ちは手順 4 で渡し直す。組み立て直した計画には、「経過」に書いた待たせた行と設計 doc の CL の対応を、同書の「設計 doc の直しを問う質問」の項の鍵で書く — 組み立て直しは issue を閉じる CL から行を作るので、ここで足さないと対応が落ちる。CL 計画は、goal が引く issue を閉じる open の CL から組み立て直す (CL の head と base から branch と target、issue 参照から行と issue の対応、worktree の path は「経過」の起動の行と `git worktree list` から)。組み立て直した計画は、同書の手順 3 の計画の記録の形 (形は同書の `scripts/cl-plan.py --help` の計画の file が正本。行の名前と `deps` と `merge_in` は「経過」の起動の行から (直した後の値を書いた行があれば、その行の最後の値から) 引き、「経過」に起動の行がある merged と closed の CL も行に含める) で作業ツリーの外の file に書き、その path を「経過」に書く — 同書の「merge に追従する」がその file を読む。「経過」に起動の行があるのに open の CL が無い issue (見送ると人が決めた issue と、CL が merge されずに closed になった issue を除く) は、新しい行として起動しない。worktree に未 commit の変更があれば、扱いを手順 4 で判断待ちに積む。無ければ、既存の branch を渡して起動し直し、実装の続きを頼む。前のセッションが起動した CL エージェントは再開しないので、その行へ送る依頼ができたときにだけ、同書の「SendMessage で CL エージェントが再開しないとき」の段落に従って起動し直す

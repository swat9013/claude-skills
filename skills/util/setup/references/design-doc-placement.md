# 設計 doc の置き場の節

対象 repo の `docs/agents/domain.md` に置く「設計 doc の置き場」節の正本。変更を設計 doc に照らす読み手 (issue の検査・差分のレビュー・指示文の検証・設計を詰める対話) は、この節が案内する設計 doc だけを読み、節が無いか設計 doc を 1 つも案内しなければ照らさない。設計 doc とは、目的・境界・ユースケース・ドメインモデルなど、変更が沿うべき設計を書いた文書を指す。

## 雛形

`docs/agents/domain.md` の末尾に、次の形の節を置く。表の行は例なので書かず、手順で答えを得た設計 doc ごとに 1 行を書く。

```markdown
## 設計 doc の置き場

| 置き場 | 適用範囲 | 索引 |
|---|---|---|
| `docs/design/payment/` | `src/payment/**` | `README.md` |
```

- 読み手が各列をどう読むか (除外の文・空欄の扱い・重なる行の当て方) の正本は、原則 leaf `${CLAUDE_SKILL_DIR}/../../knowledge/principle-index/references/leaves/principle-design-conformance.md` の「設計 doc の置き場の引き方」。利用者に列の意味を説明するときは同節を Read して伝える
- path の書き方: `置き場` は repo root 相対、`索引` は置き場からの相対

適用範囲は利用者に確かめる。読み手は変更の path が適用範囲に当たる行の設計 doc だけを当てるので、広すぎると関係の無い変更まで設計 doc に照らされ、狭すぎると照らすべき変更が照らされない。

## 突き合わせ (節が既にあるとき)

repo が書いた行は、承認された変更提案の分だけ書き換える。変更提案にするのは次の 2 つ。

- 節の見出しか表の列 (`置き場` / `適用範囲` / `索引`) が雛形と違う: 雛形の形へ揃える提案を、現状 / 提案 / なぜ違うか の 3 点で示す。形が違うと、読み手が節を読めず設計 doc に照らさない (旧い列名 `縛る対象` だけは読み手が同じ列として読むが、揃えておけば読み替えに頼らずに済む)
- 行の `置き場` か、空でない `索引` (`置き場` からの相対) が指す path が repo に無い (空の `索引` は照らさない): その行を外すか、移った先の path へ直すかを提案する。移った先は利用者に尋ねる — path の規約で探した候補を出すと、手順の「利用者が名指したものだけ」と同じく、設計 doc でない文書が案内されうる。指す先の無い行は、読み手に読めない設計 doc か入口を案内し続ける

`適用範囲` のセルの中身は照らさない — repo が自分の設計に合わせて決める値で、glob で書けない除外の文も含みうるので、雛形と比べる基準が無い。

# issue 本文の書き換え

issue 本文を書き換え、旧本文を逐語で記録する手順。同じ issue を他の書き手 (別の triage セッション・無人の worker・人) が同時に触りうるので、書き戻す前と後に本文を確かめて競合を検知する。一時 file は作業ツリーの外に置く (置き場は呼び出し元が決め、決めていなければ `mktemp` で作る)。コマンド例は GitHub (`gh`) の綴りで、他の tracker なら読み替える。

## 基準の保存

書き換え案を作る前に、`gh issue view <N> -R <issue 置き場> --json body --jq .body` で本文を file に保存し、書き換え案はこの file の本文を元に作る。この file が書き戻す直前の比較の基準になる。別の取得で読んだ本文を書き換え案の元にしない — 二つの取得の間に入った他の書き手の編集を、比較で検知できなくなる。

同じ issue を続けて書き換えるときは、前回の書き戻しの読み直しで一致を確かめた本文 (前回書いた file) を次の基準にする。読み直しより後に他の書き手が入れば、次の比較で検知される。

## 書き戻し

1. **外す label を先に外す。** 本文の状態を表す label のうち、呼び出し元の手順が外すと決めたものは、比較より先に外す (外す label が無い呼び出し元もある)。付ける label (着手可を含む) は、手順 5 の読み直しが済んでから付ける — 着手可は「検査を通った本文をそのまま実装してよい」という保証なので、この順にすると、手順 2 か 5 で止めたときに検査を通っていない本文へ着手可が付いたまま残らない
2. **比べる。** 書き戻す直前に同じコマンドで本文を別の file に保存し、基準の file と diff で比べる (末尾の空白と改行コードの違いは無視する)。食い違えば、他の書き手と競合しているので書き戻さずに止める
3. **書き戻す。** 書き換え後の本文を file に書き、`gh issue edit <N> -R <issue 置き場> --body-file <file>` で書き戻す
4. **旧本文を記録する。** 次の形のコメントを file に書き、`gh issue comment <N> -R <issue 置き場> --body-file <file>` で投稿する。旧本文は基準の file から写す — context から書き起こすと逐語が崩れる。投稿が失敗したら、基準の file の path を添えて人へ報告し (宛先は呼び出し元の手順が決める)、手順 5 へ進む

   ```
   旧本文の記録 (現行の仕様ではない)

   <書き換えた理由>

   <details><summary>旧本文</summary>

   <基準の file の中身を逐語で>

   </details>
   ```

5. **読み直す。** 本文をもう一度保存し、手順 3 で書いた file と比べる (末尾の空白と改行コードは無視する)。食い違えば、書き戻しの後に他の書き手が入ったので、以降の操作を止める

## 停止の扱い

手順 2 か 5 で止めたら、以降の操作 (書き換え・label の変更) を行わず、人へ渡す。渡し方は呼び出し元の手順が決め、label を動かしてよいのはその渡し方が決めた付け替え (人の判断待ちを表す label を付ける等) だけにする。それ以外の label は止めた時点のまま残す (外した label を戻さない・状態の label を付け直さない) — 競合した本文がどの状態に当たるかは、人が本文を読むまで決まらない。渡す内容は次の 4 つ。

- 停止理由 (比較か読み直しのどちらで食い違ったか)
- label の現状 (手順 1 で外した label の一覧)
- まだ反映していない操作
- 次に人がやること (本文と label を確かめ、状態を付け直すか triage をやり直す)

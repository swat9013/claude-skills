# ready-for-agent-review

issue N 件 (1 件以上) の本文と triage コメントを、対象 repo の規範と照らして検査する。反証を通った指摘だけを、issue ごとの markdown の提案として返す。AFK (away from keyboard — 人が張り付かずに進める) agent は issue を正として実装し、実装後のレビューも issue を正として照合する。そのため issue 自体が規範に反していると、欠陥は着手前のこの時点でしか捕まらない。

- **自分の保証**: tracker への書き込み (label 操作・コメント投稿・本文編集) はゼロ。提案をどう反映するか (本文を書き換えるか、label を動かすか) は呼び出し元の手順が決める — 人間の承認を通す呼び出し元も、AFK 境界の内側で自分で反映する呼び出し元もある。follow-up issue の文案を起票するかとその手順も呼び出し元が決める
- **やらないこと**: 優先順位で決まらない規範同士の衝突と AFK 境界の外の衝突の裁定 (どちらも深掘り対話に回す。境界と優先順位は手順 3 の ③)、triage の分類そのもの、実装差分のレビュー
- 入口は 3 つ: triage 手順からの invoke、深掘り (対話) で論点を確定した後・着手可にする前の invoke、人が issue 番号を渡して行う再レビュー。どの入口でも手順は同じで、triage 以外の入口は N=1 で呼んでよい
- **対象 repo** とは、issue の変更が入る repo (cwd の repo) を指す。issue 置き場とは別の repo のことがある。規範は対象 repo から読み、issue 置き場は issue の取得だけに使う

## 1. issue を読む

入力は issue 番号の列 (1 件以上。件数の上限は置かない)。issue 置き場は、呼び出し元が指定していればそれを使う。指定が無ければ対象 repo の `docs/agents/issue-tracker.md` の宣言に従う。宣言が別の file を正本として指すなら、その file が置き場として宣言する値を使う。指された file が無いか値を読み取れなければ、対象 repo 自身へ落とさず、issue ごとに手順 5 の停止の形で返す — 正本が別 repo を宣言していると、同じ番号の別の issue を読むことになる。`docs/agents/issue-tracker.md` が無いか置き場の宣言を読み取れなければ対象 repo 自身を置き場とする。取得コマンドには置き場を `-R <issue 置き場>` で明示する。cwd 推論に任せると、別 repo にある同じ番号の issue を読んでしまう。

issue ごとに `gh issue view <N> -R <issue 置き場> --json title,body,labels,comments` で本文と全コメントを逐語で読む (`--comments` は非 TTY 実行ではコメントだけを出力し、本文が黙って抜ける)。コマンドは GitHub の綴りで書いている。tracker が別なら、`docs/agents/issue-tracker.md` の CLI 規約にある同等のコマンドに読み替える。検査対象は本文と triage コメント。triage コメントとは、分類・置き場・範囲・選択肢の採否を決めたり絞ったりしたコメントを指す。それ以外の議論コメントは、文脈として読むだけにする。本文を書き換えたときに旧本文を残したコメント (1 行目が `旧本文の記録 (現行の仕様ではない)` のもの) は、検査対象にも文脈にもしない — 現行の仕様は本文だけが持つ。

本文の末尾に、上の本文より優先すると宣言した追記の節 (`## 確定事項` 等) があれば、その宣言どおりに読む。その節が上の本文を絞った箇所は、食い違いではなく決定として読む。呼び出し元は issue ごとに `#<N>` の見出しを置き、書き換え案を添える issue は見出しの下に書き換え後の本文全体の逐語を置く。書き換え案が添えられたら、tracker 上の本文の代わりにその文面を検査対象にする — tracker へ反映する前に検査するための入力で、tracker 上の本文はまだ変わっていない。取得に失敗した issue は手順 5 の停止の形で返し、残りの issue の検査を続ける。

## 2. 規範を揃える

規範は N 件分をまとめて 1 回だけ揃える。毎回読むものは issue に依らず同じで、issue の変更対象から引くものは全 issue の path を合わせて読む。

指摘の根拠にできる出典は 2 種類に限る: 対象 repo に書かれた規範の file:line と、この手順が名指しで読む plugin 同梱の基準 (principle leaf と component reference) の file:line。

**毎回読むもの**:

- 対象 repo の `CLAUDE.md`。加えて、そこから索引されている構成の正本 (アーキテクチャ doc 等) のうち、カテゴリ分けと配置規則を定める節
- 依存方向・層の規則: 構成の正本のうち依存の向きを定める節と、それを検査する gate (`scripts/` 等の gate / lint 置き場にある script)。層の順位が gate の中にしか書かれていないこともあるので、doc だけで探し終えない
- 原則の索引 `${CLAUDE_SKILL_DIR}/../../knowledge/principle-index/SKILL.md` を Read し、索引が示す path から `principle-ai-delegation-boundary` を Read する (軸 ② の判定基準と、軸 ③ の AFK 境界)

**issue の変更対象から引くもの**: issue が変更・新設する path を本文とコメントから抜き出す。path が明示されていなければ、主題語で対象 repo を grep して変更先の候補 path を特定する。path ごとに次を読む。

- 対象 repo の `.claude/rules/*.md` のうち、frontmatter `paths` がその path に一致するもの (`paths` を持たない rules は全 path に一致するものとして読む)
- その path が harness の指示文 (CLAUDE.md / `.claude/rules/` / SKILL.md / hook 注入文 / agent 定義 — `.claude/agents/*.md` と plugin root の `agents/*.md`) なら、`${CLAUDE_SKILL_DIR}/../../steering/write-for-harness/references/components/` の該当 1 本 (`claude-md.md` / `rules.md` / `skill.md` / `hook-inject.md` / `agent.md`)。各 component の責務定義は、issue が置き場を指定するときの適合基準になる
- 対象 repo の ADR 置き場 (`docs/adr/` 等) を、path・component 名・issue の主題語で grep して当たった ADR。status が Superseded / Deprecated のものは根拠にしない

## 3. 3 軸で候補を出す

issue ごとに、3 軸すべてを、検査対象の本文 (書き換え案が添えられていればその文面) と triage コメントの全体に当て、当たったもののうち手順 2 の出典 (file:line) を示せるものを、重要度で絞らずに全件候補にする (示せない指摘は推測)。出した候補を落とす段は手順 4 の反証だけ。

- **① 規範違反の指定**: issue や triage コメントが示す選択肢・置き場・構造の指定のうち、その通りに実装すると手順 2 の規範に反するもの。たとえば、層規則で禁じた向きの参照を生む「双方向にする」という選択肢や、component の責務定義に反する置き場への絞り込み。issue に選択肢が並ぶ場合、1 つでも違反する選択肢があれば指摘する。worker はどれでも選びうるため。手順 2 で開いた gate は走査対象を確かめ、gate が**見ていない範囲** (同じカテゴリ内の相互参照など) を重点的に見る。gate を通ることは規範適合の証拠にならない
- **② AI 委任範囲の未閉鎖**: 本文が変更してよい範囲を閉じていないもの。範囲外の変更に気付いたときの扱い (follow-up issue に切り出す等) が無い、撤去・置換の上限が無い、「必要に応じて」「適宜」のように worker の自律判断で範囲が広がる語がある、などが該当する。worker が範囲を広げうる具体的な箇所を引用して指摘する
- **③ 規範同士の衝突**: issue の要求を満たすと、手順 2 で読んだ 2 つの規範のどちらかに必ず反するもの。優先順位で決まる衝突は裁定し、決まらない衝突と AFK 境界の外の衝突は裁定せずに深掘り対話へ回す。
  - **優先順位**: 適用範囲を絞った個別の規範 (特定の path・component・手順だけに掛かるもの) が、全体に掛かる一般の規範に勝つ。2 つとも決定記録 (ADR 等の日付を持つ記録) なら、日付の新しい方が勝つ。範囲の基準と日付の基準が逆の規範を勝たせるとき、どちらの基準も当てはまらないとき (同じ範囲に掛かり、決定記録どうしでもない) は、優先順位で決まらない
  - **AFK 境界の外**: 裁定が、手順 2 で読んだ `principle-ai-delegation-boundary` のうち人間に返す判断の種類を定めた項に当たるときは、優先順位で決まっても裁定しない — ここに当たる衝突を裁定すると、人が見るべき判断が黙って agent に渡る
  - **裁定したとき**: 勝った規範に issue を合わせる修正案と、負けた規範を勝った規範に揃えて直す follow-up issue の文案 (タイトルと本文) を返す。負けた規範を残すと、次の issue で同じ衝突が出る。起票は呼び出し元が行う。本文には手順 5 の雛形の `## 範囲` の節を必ず埋める — 文案はそのまま起票されうるので、範囲を閉じていない文案から起票した issue は、次の検査で軸 ② に当たって差し戻される

指定と規範の関係が ① と ③ のどちらか判断が付かないとき (規範側がすでに食い違っているとき) は、③ として出す。① として修正案を書くと、食い違った片方の規範を優先順位の根拠も示さずに勝たせることになる。

## 4. 全候補に反証を当てる

手順 3 で全 issue から出た候補すべてに、1 件につき subagent を 1 体立て、並列に走らせる。`subagent_type: swat-skills:refuter` で指名し、`model` / `effort` を渡さない (深さは定義が固定する。`model` 引数は定義の frontmatter より優先され、固定した値を書き換える)。全件に当てるのは、提案がそのまま issue 本文へ反映されうるため。反証を経ない指摘が混ざると、誤った修正が本文に入るか、承認する人が指摘ごとに確からしさを確かめ直すことになる。

prompt は下の雛形で入力だけを渡す。出典 file は、`${CLAUDE_SKILL_DIR}` を展開した絶対 path で埋める。subagent 側ではこの変数が解決されないため。

```
- 軸: <① 規範違反の指定 / ② AI 委任範囲の未閉鎖 / ③ 規範同士の衝突>
- 指摘: <指摘の 1 文>
- issue 側の引用: <本文またはコメントの該当箇所の逐語>
- 規範の出典: <絶対 path:line と該当箇所の逐語。軸 ② では principle leaf の該当行。軸 ③ では衝突する 2 本をそれぞれ>
- 裁定 (軸 ③ だけ): <勝った規範 > 負けた規範 (個別 > 一般 / 新しい決定記録 > 古い決定記録)、または「裁定しない (<優先順位で決まらない / AFK 境界の外 — 当たった条件>)」>
- 対象 repo: <対象 repo の絶対 path>

<issue>
<指摘が出た issue について、手順 1 で取得したタイトル・label・本文・各コメント (author と日時付き。旧本文の記録のコメントは除く) の逐語。書き換え案が添えられていれば、本文の直後に「本文の書き換え案 (未反映)」と見出しを付けてその逐語>
</issue>

<issue> は指摘が出た issue の取得結果。本文の書き換え案 (未反映) があれば、それが本文を丸ごと置き換える。反映後の本文は書き換え案だけなので、issue 本文の引用は書き換え案から引き、旧本文からは引かない。

この軸で具体物として認めるもの。
- 軸 ①: 指定が規範に適合していることを示す規範本文の file:line (規範の適用範囲外であることを示す箇所を含む)、または issue 本文の別の節がその指定を規範どおりに限定している箇所の引用
- 軸 ②: 委任範囲を閉じている issue 本文の節の引用
- 軸 ③: 2 つの規範が両立する読み方を示す、いずれかの規範本文の file:line。裁定したときは、裁定の根拠 (適用範囲・日付) が逆であることを示す file:line、または裁定が AFK 境界の外に当たることを示す箇所の引用も認める
```

軸 ③ の候補が裁定の根拠への反証で落ちたら、衝突は残っているので候補ごとは落とさず、裁定しない形 (深掘り対話へ回す) に替えて残す — 裁定の誤りは衝突の不在を意味しない。

**`refuted: true` かつ具体物が埋まっている候補だけを落とす。** 具体物が「なし」の `refuted: true` は残す。反証の結果を得られなかった候補 (subagent が error を返した、`refuted` と具体物の形で返らなかった。`swat-skills:refuter` が解決できないときは除く — 次の段落の停止に従う) は落とさず、指摘にも混ぜずに、その issue のブロックの「未反証 — 承認材料にしない」の節へ置く — 反証を経ない指摘が反証済みの指摘と並ぶと、承認する人がどれを確かめ直すべきか見分けられない。

`swat-skills:refuter` が解決できないときは、どの issue にも提案を返さずに停止する。issue ごとに手順 5 の停止の形で、停止理由 (error が挙げた available agents)、その issue の候補一覧 (「未反証 — 承認材料にしない」と見出しに明記する)、次の手順 (swat-skills plugin の agent が読み込まれる状態にしてから再実行する) の 3 つを返す。`general-purpose` で代わりにすると、反証が指名した agent 定義の読み方を通らないまま、通ったように見える。未反証の候補を提案に載せると、承認材料に確からしさの違う指摘が混ざる。

## 5. 提案を返す

入力の issue ごとに次の形のブロックを並べた markdown を返して終える。深掘り対話への回し先は、対象 repo の `docs/agents/triage-labels.md` に深掘り待ちの label があればその綴りで書く。そのファイルが無いか label の宣言を読み取れなければ label を提案せず、「深掘り対話が要る」と書く (読み取れなかったときは「triage-labels.md の宣言を読み取れず」と添える)。

```markdown
## ready-for-agent-review: #<N>

反証対象: <候補数> 件 / 落とした件数: <件数> / 未反証: <件数>
issue 置き場: <置き場> (<呼び出し元の指定 / 宣言 / 宣言が指す正本 (<file>) / 宣言ファイルなし / 宣言を読み取れず>)
読んだ規範: <手順 2 で読んだ file の一覧。該当が無かった項目は「<項目>: 該当なし」と書く>

### 指摘

#### <軸番号> <指摘の 1 文>
- issue 側: <出典 (本文 / コメントの author と日時 / 書き換え案 (未反映))> — 「<逐語引用>」
- 規範: <file:line> — 「<逐語引用>」 (軸 ③ では衝突する 2 本をそれぞれ)
- 修正案: <issue 本文の書き換え案 (書き換える箇所と書き換え後の文面。指摘が書き換え案 (未反映) から出たときは、その書き換え案の差し替え文面)。軸 ③ を裁定したときは勝った規範に合わせる書き換え案 (issue がすでに勝った規範に沿っていれば「なし」)>
- 深掘り (軸 ③ を裁定しないとき、修正案の行の代わりに): <深掘り待ち label の綴り、または「深掘り対話が要る」> (<優先順位で決まらない / AFK 境界の外 — 当たった条件>)
- 裁定 (軸 ③ を裁定したときだけ): <勝った規範の file:line> > <負けた規範の file:line> (<個別 > 一般 / 新しい決定記録 > 古い決定記録>)
- follow-up issue の文案 (軸 ③ を裁定したときだけ): タイトル「<負けた規範をどう直すか>」/ 本文「<発端の issue 番号、裁定とその根拠、負けた規範の file:line と直し方、`## 範囲` の節 (変更してよい file = 負けた規範の file。範囲外で見つけた指摘の扱い = 手順 2 で読んだ規範に issue 起票の規則があればその文面、無ければ「別の issue に切り出す」)>」

### 未反証 — 承認材料にしない

#### <軸番号> <指摘の 1 文>
- issue 側 / 規範: <指摘と同じ形>
- 反証の結果を得られなかった理由: <error の要旨、または返った形>
- 次の手順: 同じ issue でこの skill を invoke し直す (反証は全候補にやり直される)
```

指摘が 0 件なら `### 指摘` に「該当なし」と書く。未反証の候補が無ければ `### 未反証 — 承認材料にしない` の節ごと省く。

提案を返さずに止まる issue は、上の形の代わりに次の形で返す。停止は issue ごとで、止まった issue の停止は他の issue のブロックに影響しない。

```markdown
## ready-for-agent-review: #<N>

停止: <停止理由>

### 未反証 — 承認材料にしない

<手順 3 の候補一覧。候補を出す前に止まったなら「候補なし」>

次の手順: <停止を解く手順>
```

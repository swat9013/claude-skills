# prompting-principles

Claude に渡す指示文の**文面**をどう書くかの決定規則。skill 本文・hook のメッセージ・subagent への依頼文・CLAUDE.md / rules・API システムプロンプトのいずれも対象。

責務境界:

- **skill ファイルとしての作法** (frontmatter・invocability・配置・trigger 語彙・参照の実在) は `claude-config-review` skill の [skill reference](../claude-config-review/references/skill.md) が正本。本 skill は「その本文に何をどう書くか」だけを扱う
- **どのモデルを選ぶか** (能力帯・単価比・モデル ID・`model:` frontmatter の選定・long-context 現象) は同 skill の [models reference](../claude-config-review/references/models.md) が正本。本 skill にモデル ID は書かない
- 対象モデルが確定しているときだけ、末尾のモデル別 reference に降りる

## メタ規則 (最優先)

- **足すより引く。** 現行モデルが既定でやることを指示に書くと、重複した挙動が増幅されてトークンとレイテンシだけが増える。まず既定で足りるかを確かめ、足すのは観測した逸脱に対してのみ
- **予防的な指示を書かない。** 「念のため」の禁止則・徹底化・強調は、抑えたい挙動ではなく別の過剰挙動を作る
- **指示の効果は測ってから確定する。** 文面を変えたら、変えた前後で対象の逸脱が消えたかを確かめる。skill 本文なら圧力シナリオの subagent micro-test で、指示なし control と比較する

## 既定で足りるので書かない

旧世代向けに書いた指示は、現行モデルでは害に転じる。移行時は以下を**削除**する (書き直すのではなく消す)。

- **自己検証・再チェックの指示** (「応答前に再検証しろ」「検証ステップを含めろ」「subagent で検証しろ」) — 現行モデルは指示なしで自分の作業を検証する。残すと過剰検証になる。ハーネス側に足した検証ステージのスキャフォールディングも同じ
- **徹底化・怠惰対策** (「必ず全部読め」「迷ったらこの tool を使え」) — 現行モデルはツールを十分に呼ぶ。この種の指示は過剰トリガーを生む。**例外は thinking を切った構成** — 思考を無効化すると tool に手を伸ばしにくくなるので、そのときだけ明示的な促しを残す (使う条件を具体で書く。「迷ったら」は条件ではない)
- **中間ステータスの強制** (「tool 呼び出し 3 回ごとに進捗を要約しろ」) — 既定で報告する。強制は報告の質を下げる
- **強調語の盛り** (`CRITICAL: You MUST ...`) — 平叙な「Use this tool when ...」に落とす。現行モデルはシステムプロンプトへの反応が強く、強調はトリガー過剰に直結する
- **内部推論の再現要求** (「思考過程を書き出せ」「なぜそう判断したか復唱しろ」) — 上位モデルでは拒否カテゴリを踏み、thinking を切った構成では内部タグが可視出力に漏れる。途中経過が要るなら thinking block を読むか、逐語表示用の tool を別に用意する
- **prefill / 手動 thinking budget を前提にしたスキャフォールディング** — 現行モデルでは受け付けられない。出力形式の強制は構造化出力か tool 定義へ、思考量の制御は effort へ移す

## 文面で制御するか parameter で制御するか

効かない指示を書き続ける原因はこの境界の誤りが多い。

- **文面でしか動かないもの**: 応答の長さ・ナレーションの量とタイミング・ディスクに書く成果物ドキュメントの長さ・トーン・文体の多様性。effort を下げても可視出力は縮まない。sampling parameter に頼るのもやめる (現行モデルでは受け付けられない場合がある)
- **effort が主軸のもの**: 思考の深さ・事前探索の量・ツール使用の積極性。浅い推論を文面で埋めようとせず effort を上げる。逆に思考が膨らみすぎるなら effort を下げる
- **例外**: レイテンシ都合で effort を上げられないときだけ、「この課題は多段推論が要る」と 1 行だけ文面で補う

## 何をどう書くか

- **望む結果を具体的に書く。** 曖昧な指示からモデルが推測することに賭けない。判定基準は「その仕事の文脈を持たない同僚に渡して混乱するなら、モデルも混乱する」
- **理由を添える。** 「なぜそうしてほしいか」があると、モデルは列挙しなかったケースへ一般化する。「省略記号を使うな」より「読み上げエンジンが発音できないので使うな」
- **肯定形で書く。** 望む振る舞いの正例が、禁止則より効く。禁止則は列挙漏れから破れる。「markdown を使うな」ではなく「流れる散文の段落で書け」
- **量的制約より質的原則。** 「質問は 1 つまで」ではなく「質問攻めにしない」。数値は逸脱が数で測れるときだけ使う
- **スコープを明示する。** 現行モデルは指示を文字通りに解釈し、ある箇所への指示を他へ勝手に一般化しない。全体に効かせたいなら「最初の節だけでなく全節に適用する」と書く
- **絞り込みの語を軽く使わない。** 「重大なものだけ報告しろ」「保守的に」と書けば、文字通り報告を絞る。網羅させたいなら「全件出す段」と「フィルタする段」を分け、網羅段では「重要度で落とすな」と明示する
- **領域が混ざるなら XML タグで区切る。** 指示・文脈・入力・例をタグで分ける。長い入力は先に、指示は後に置く
- **例示は 3〜5 個。** 実ケースを反映し、エッジケースを含めて多様に。`<example>` で囲んで指示と区別する
- **指示文の見た目が出力に伝染する。** 箇条書きを減らしたいなら、指示文自体の箇条書きを減らす

## エージェントとして動かす指示

- **提案か実行かを既定として書く。** 「〜を提案して」と書けば提案で止まる。実装させたいなら「〜を変更しろ」と書く。既定を決めるなら「曖昧なら最も有用な行動を推測して進む」か「曖昧なら調査と推奨に留める」のどちらかを明示する
- **確認を要求する範囲は不可逆・共有影響に限る。** 可逆なローカル操作 (ファイル編集・テスト実行) を止めない。全部確認させると自律性が死ぬ。破壊的操作・元に戻しにくい操作・他人に見える操作を例示して線を引く
- **停止条件を書く。** 停止してよいのは「不可逆な操作の直前」「本当のスコープ変更」「ユーザーしか出せない入力」。約束 (「では〜します」) で turn を終わらせず、その場で実行させる
- **委任の線を引く。** subagent は並列化できる・独立した文脈が要る大きな作業だけ。数手で終わる作業や自分の作業の検証を委任させない。上限を決めるなら文面ではなく決定論的な上限で縛る
- **長時間実行では進捗の裏取りを要求する。** 「報告する前に、各主張をこのセッションの tool 結果に突き合わせろ。裏が取れないものは未検証と明示しろ」型の指示は、捏造された進捗報告をほぼ消す
- **過剰設計の抑制は名指しで書く。** スコープ (頼まれていない改善をしない)・防御的コード (起こり得ない状況の検証を足さない)・抽象 (1 回の操作にヘルパーを作らない) の 3 点を具体的に挙げる。「シンプルにしろ」だけでは効かない

## 本文様式の選び方

- 圧力下で破られる**規律**の失敗には禁止則を書く。出力の**形**が崩れる失敗には手順・雛形を書く。判断の質を担保したい対話・思考系には**原則**を並べる
- 迷ったら原則側に倒す。指示追従が強いモデルではルールを増やすほど文字通り従い、書き漏れた領域が空白になる
- どちらを選んでも束縛力は micro-test で確かめる (メタ規則 3)

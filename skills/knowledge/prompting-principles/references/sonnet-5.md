# Sonnet 5 に向けて書くときの差分

対象モデルが Sonnet 5 と確定しているときだけ読む。**本 doc は差分層** — 判断規則の正本は SKILL.md 本文で、ここは本文で足りない挙動差と、それに対応する公式サンプル prompt を判断の素材として引用形で残す層。共通原則を再掲しない。

## 削る指示・スキャフォールディング

- **中間ステータスの強制** (「tool 呼び出し 3 回ごとに進捗を要約しろ」) — 長いエージェント実行中に定期的で質の高い更新を自分で出す。強制は外してから、更新の中身が用途に合わなければ「どういう更新が欲しいか」を例つきで書く
- **sampling parameter** — `temperature` / `top_p` / `top_k` を既定以外にすると 400 になる。トーンと多様性はシステムプロンプトの文面で作る
- **手動 thinking budget** — 400 になる。effort による適応的思考に置き換える

## 応答長は自動で追従する

固定の冗長性を既定に持たず、タスクの複雑さに応じて長さを変える (単純な検索は短く、自由度の高い分析は長く)。特定のスタイルに依存した製品だけ再調整する。減らすなら「本質でない文脈は省き、例は最小限に」型。**望ましい簡潔さを示す正例が、禁止形の指示より効く。**

## effort を厳守する — 思考不足は文面で埋めない

effort レベル、特に低い側を厳密に守る。`low` / `medium` では期待以上のことをせず、求められた範囲に作業を限定する。レイテンシとコストには良いが、中程度に複雑なタスクを `low` で回すと思考不足のリスクがある。

- **浅い推論を観測したら、文面で回避しようとせず effort を `high` / `xhigh` に上げる**
- レイテンシのために `low` を保つ必要があるときだけ、「この課題は多段推論が要る。答える前によく考えろ」と 1 行だけ足す
- 逆に思考ブロックが望むより頻繁なら、「思考はレイテンシを増やすので、答えの質が有意に上がるとき (多段推論が要る問題) だけ使う。迷ったら直接答える」と抑える
- effort の対応関係はモデル間で名前が一致しない。ベンチマークは effort 名ではなく**観測された思考の長さ**で対応付ける

## thinking が既定で有効になった影響

`thinking` フィールドなしのリクエストは適応的思考で走る。旧モデルで thinking なしを前提にしていたワークロードは見直す。

- `max_tokens` は思考 + 応答テキストの合計上限。high 以上の effort では余裕を持たせる。予算が厳しいと「ほぼ全部思考 + 切り詰められた回答」になる
- **同じ文章に対して約 3 割多いトークンを生成する新トークナイザー** を使うので、旧モデル向けに詰めた `max_tokens` は同等の出力を切り落とす
- **thinking を切ると tool に手を伸ばしにくくなる**。切った状態で tool 呼び出しに依存するなら、システムプロンプトに明示的な促しを足す。effort も tool 使用のレバーで、high / xhigh では agentic な検索とコーディングでの tool 使用が大幅に増える

## 文字通りの指示追従

プロンプトを文字通り・明示的に解釈する。ある項目への指示を別の項目へ暗黙に一般化せず、していない要求を推測しない。**利点は精度** (慎重に調整したプロンプト・構造化抽出・予測可能さを求めるパイプラインで有利)。

- 広く効かせたいならスコープを明示する: 「この形式を最初の節だけでなく全節に適用しろ」
- **レビュー系ハーネスで recall が落ちたら能力後退と読まない。** 「重大度の高い問題のみ」「保守的に」「細かいことは指摘するな」に忠実に従い、同じ深さで調べて発見はしているが報告に変換しないだけ。網羅させる文面に変える:

> 見つけた問題は、確信が持てないものや軽微と判断したものも含めて全件報告する。この段階で重要度や確信度でフィルタしない (別の検証段が行う)。目標は網羅性で、後で落とされる発見を出すほうが、実バグを黙って落とすよりよい。各発見には確信度と推定重大度を添える。

単一パスで自己フィルタさせたいなら、「重要」のような定性語ではなく基準の位置を具体で示す (「誤動作・テスト失敗・誤解を招く結果につながり得るバグは全部報告し、純粋なスタイルや命名の好みだけ省く」)。

## デザイン・フロントエンドの既定

自由度の高い要件では一貫した既定のビジュアルスタイルに落ち着く。**一般的な否定 (「その色を使わないで」「クリーンでミニマルに」) は多様性を生まず、別の固定パレットへ移すだけ。** 確実に効くのは 2 つ:

1. **具体的な代替案を仕様として渡す** — 色の hex 範囲・書体の性格・角丸の px・余白の方針・節構成まで書けば正確に従う
2. **作る前に案を出させる** — 「作り始める前に、この要件に沿った 4 つの異なる方向性を (背景 hex / アクセント hex / 書体 + 1 行の根拠) で提案し、ユーザーに選ばせてから、選ばれた 1 案だけ実装する」。`temperature` が使えないため、実行ごとに意味のある差を出す推奨手段はこれ

## インタラクティブなコーディング用途

- 性能とトークン効率を両立させるなら effort は `high` / `xhigh`、加えて自律機能を足して人間の介入回数を減らす
- **最初の人間のターンでタスク・意図・制約を出し切る**。複数ターンに小出しにした曖昧な指示はトークン効率を下げ、性能も落ちることがある

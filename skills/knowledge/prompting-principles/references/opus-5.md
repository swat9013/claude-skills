# Opus 5 に向けて書くときの差分

対象モデルが Opus 5 と確定しているときだけ読む。**本 doc は差分層** — 判断規則の正本は SKILL.md 本文で、ここは本文で足りない挙動差と、それに対応する公式サンプル prompt を判断の素材として引用形で残す層。共通原則を再掲しない。

## 削る指示

- **自己検証・再チェックの指示**: 指示なしで自分の作業を検証し、ミスを見つけて直す。「答えを再確認しろ」「応答前に再検証しろ」「非自明なタスクには最終検証ステップを入れろ」「subagent で検証しろ」は書き直さず削除する。品質を落とさずトークンとレイテンシが減る。ハーネス側に足した独立の検証ステージも同じ
- **「思考するな / 推論するな」のルール**: thinking を無効化した構成でこれを書くと、内部 XML タグの可視出力への漏れが増える

## 冗長性は文面でしか縮まない

既定のユーザー向け応答が旧世代より長い。**effort は「どれだけ思考するか」を制御するもので、「どれだけ喋るか」ではない** — effort を下げても可視応答は確実には短くならない。

- 短い簡潔さ指示で足りる。「回答本体に分量を使い、注意書きは短く。説明を求められたら、詳細を明示的に要求されない限り高レベルの要約を返す」型
- 長いシステムプロンプトでは、末尾近くに短いリマインダー (「出力は程よく簡潔に」) を対で置く
- **会話の冗長性と成果物の長さは別問題**。ディスクに書くレポート・Markdown も長くなるので、必要なら「中身は網羅するが、埋め草の節・重複した要約・定型文で膨らませない」と別に指示する

## ナレーションは望むペースと形式で書く

エージェント作業中に積極的にナレーションする (これから何をするかの宣言が多い)。抑えるなら「何をしないか」ではなく望む形を書く:

> 最初の tool 呼び出しの前に、これからすることを 1 文で言う。作業中は重要な発見か方針転換のときだけ短く報告する。終わったら結論から始める (1 文目が「何が起きたか / 何が分かったか」に答える)。

増やしたい・スタイルを変えたい場合も同じ手段を逆向きに使う。**肯定的な例が禁止則より効く。**

- **訂正のナレーションも多い**。ユーザー向け製品で邪魔なら「ユーザーのコード・結論・判断が変わる誤りだけ訂正し、変わらない言い間違いは黙って直して進む」と絞る

## スコープを勝手に広げる

要求されていない手順を足したり、タスクがどうあるべきかの独自判断を適用したりする。狭いタスクでは明示的に縛る:

> 頼まれたものを、頼まれた範囲で出す。ルーチンな判断は自分でする。解釈が分かれて成果物が大きく変わる場合だけ確認する。依頼が誤っている / より良い方法があると思ったら 1 文で述べてから、依頼どおりに続ける (勝手に狭める・広げる・別物に変えるをしない)。

## subagent の委任は明示的に線を引く

旧世代より積極的に委任する。真に独立した大きな作業では効くが、小さなタスクに使うとコストと時間が倍になる。

> 委任するのは、真に独立して並列化できる大きな作業 (広範な複数ファイル調査など) だけ。数手の tool 呼び出しで自分で終わる作業は委任しない。自分の作業の検証に subagent を使わない。1 体で足りるなら 1 体にし、起動数を低く保つ。

コストに敏感な用途では、文面より**決定論的な起動上限**をハーネス側に置く。

## thinking を無効化するときの副作用

thinking は既定で有効で、無効化できるのは effort が high 以下のときだけ。無効化すると 2 つの副作用が出る:

1. **tool 呼び出しがテキストに漏れる** — 構造化された tool_use ブロックの代わりにユーザー向けテキストへ書き、呼び出しは実行されないまま turn が正常終了する。漏れたテキストは履歴に残り後続ターンにも影響する。検索系の多用ワークロードで最も出やすい
2. **内部 XML タグが可視応答に漏れる**

**既定の緩和策は「無効化せず low effort で回す」** — ほとんどのタスクで、同程度のコストなら thinking 有効 + low effort が thinking 無効を上回る。無効化が必須の統合なら 1 本の指示で両方を緩和する:

> tool を使うときは先に短く 1 文言ってよい。求められたことを表現できる tool がなければ、推測せずにそう言う。内部・システムの XML タグを応答に含めない。

**thinking タグを名指しする指示は一般形より効果が低い** ので、タグ名を挙げない。

## コードレビューを書かせるとき

precision と recall がともに高く、低い effort でも precision が維持される (速いパス → 後で徹底パスの二段が組める)。ただし「重大度の高い問題のみ報告」「保守的に」と書くと文字通り従って報告を減らす。**全件報告させ、フィルタは別パスに分ける。**

## effort の使い方

既定は high。`low` / `medium` はわずかなトークンとレイテンシで高い品質を出すので、**コストと応答時間の主要な制御手段として積極的に使う**。要求の厳しいコーディング・エージェント作業は `xhigh` に上げる。旧モデルから effort の既定を引き継いだなら、自分の評価でスイープをやり直す。

# Fable 5 系に向けて書くときの差分

対象モデルが Fable 5 系 (Mythos 5 を含む) と確定しているときだけ読む。**本 doc は差分層** — 判断規則の正本は SKILL.md 本文で、ここは本文で足りない挙動差と、それに対応する公式サンプル prompt を判断の素材として引用形で残す層。共通原則を再掲しない。

## 文面より先にハーネスを直す

高い effort では 1 リクエストが数分走り、自律実行は数時間に及ぶ。**移行時に最初に触るのは文面ではなくハーネス** — クライアントの timeout・streaming・進捗インジケータを調整し、実行の確認をブロッキングではなく非同期 (スケジュールされたジョブ等) に組み替える。

## 指示は 1 個ずつ列挙しない

指示追従が十分に強いので、**簡潔な指示 1 本で挙動群をまとめて制御できる**。挙動をパターンごとに名指しして並べるのは、同じ効果でプロンプトを膨らませるだけ。

- 冗長さの抑制 (採らない選択肢の調査・長い根本原因説明・過度に構造化された PR 説明・自明なコメント) は「結論から書く。要点を先に、根拠は後。読みやすさと短さは別で、読みやすさが優先」型の 1 本で足りる
- チェックポイントも全ケースを列挙しない: 「本当にユーザーが必要なとき (不可逆な操作・本当のスコープ変更・ユーザーしか出せない入力) だけ止まる。止まるなら訊いて turn を終える。約束で終わらせない」
- 曖昧なタスクでの過剰計画も同型: 「動ける情報が揃ったら動く。既に確定した事実を再導出せず、決着済みの判断を再燃させず、採らない選択肢をユーザー向けに並べない。迷っているなら網羅的な調査ではなく推奨を出す」

## 高 effort では要求外の作業が出る

effort が知能・レイテンシ・コストの主要な制御手段。既定は high、能力最重視は xhigh、定型作業は medium / low。**低い effort でも旧世代の xhigh を上回ることが多い**ので、遅いだけなら下げる。

高い effort では検証や推論が洗練される一方、タスクに必要な範囲を超えた整理・リファクタが出る。抑えるなら「機能追加・リファクタ・抽象の導入をタスクの要求を超えて行わない。バグ修正に周辺の掃除は不要、1 回の操作にヘルパーは不要。起こり得ない状況の error handling / fallback / 検証を足さない。境界 (ユーザー入力・外部 API) だけ検証する」と名指しする。

## 進捗報告を tool 結果に根拠づける

長い自律実行では、**報告前に各主張をこのセッションの tool 結果に突き合わせるよう指示する**。公式テストでは、捏造を誘発するよう設計したタスクでも捏造されたステータス報告がほぼ消えた。

> 進捗を報告する前に、各主張をこのセッションの tool 結果に照らして監査する。証拠を指せる作業だけ報告し、未検証なら明示的にそう言う。結果は忠実に報告する (テストが落ちたら出力付きで言う、飛ばした手順は飛ばしたと言う、完了して検証できたものは断定する)。

## 境界を明示する

要求していないアクション (依頼のないメール下書き、防御的な git バックアップブランチ作成など) を時折する。**やってよいこと / やらないことを明示する。**

> ユーザーが問題を説明している・質問している・考えを口に出しているだけで変更を要求していないなら、成果物はあなたの評価。所見を報告して止まる。頼まれるまで修正しない。システム状態を変えるコマンド (再起動・削除・設定変更) の前に、証拠がその特定の行動を支持しているか確かめる。既知の障害にパターンが似ているだけで原因が違うことがある。

## 並列 subagent は非同期で回す

旧世代より積極的に並列 subagent をディスパッチし、その維持も信頼できる。**subagent を頻繁に使い、各体の完了までブロックせず、オーケストレータと subagent の非同期通信を優先する。** サブタスク間で文脈を保つ長寿命 subagent はキャッシュ読みで時間とコストを節約し、最も遅い 1 体によるボトルネックを避けられる。

> 独立したサブタスクは subagent に委任し、走らせたまま自分の作業を続ける。subagent が脱線したり必要な文脈を欠いていたら介入する。

自己検証は、**自己批評より独立した新しい文脈の検証 subagent が優れる**。長時間タスクでは検証の間隔と方法を指示する (「一定間隔で仕様に対して subagent で検証する」)。

## メモリを書く場所を与える

過去の実行から得た教訓を記録し参照できると特に強い。Markdown ファイル程度で足りる。

> 1 ファイル 1 教訓、先頭に 1 行要約を置く。訂正と確認できた手法の両方を、なぜ重要だったかとともに記録する。repo や履歴が既に持っている情報は書かない。重複を作らず既存メモを更新する。誤りだと分かったメモは消す。

既存履歴からのブートストラップは「過去のセッションを振り返り、subagent で主題と教訓を抽出して [場所] に保存し、以後 [場所] を参照すると分かるようにしておく」で足りる。

## 逐語で届けたい内容には専用 tool を作る

長時間の非同期エージェントでは、**turn を終えずにユーザーへ逐語で表示する tool** (`send_to_user` 型) を用意する。入力は表示するメッセージ、呼ばれたら UI に直接描画して確認応答を返す。tool 入力は要約されないので中身がそのまま届く。

**tool を定義するだけでは呼ばれない。** システムプロンプトに誘導文を対で置く: 「tool 呼び出しの間に、ユーザーが逐語で読む必要のある内容 (部分成果物・質問への直接の回答) があればこの tool を呼ぶ。ナレーションや推論をこの tool に流さない」。定型的な進捗報告しかしないエージェントなら、モデル自身の要約で足りる。

## 最終要約は再グラウンディングとして書かせる

長いエージェント会話では、密な矢印記法・深い実装詳細・ユーザーが見ていない思考への言及など、読みにくいテキストを生む。

> tool 呼び出しの間の走り書きはよい (それは考えている最中で、短さが利点)。最終要約は別物で、その過程を何も見ていない読者に向けて書く。長く見られずに作業した後なら、最終メッセージはユーザーの最初の一目になる。作業スレッドの続きではなく再グラウンディングとして書く。結論から 1 文、それから根拠。作業中に作った語彙は自分のもので相手のものではない — 再導入しない限り置いていく。完全な文で書き、略記・矢印連鎖・自作ラベルを使わない。

## 踏み抜くと refusal になるもの

- **内部推論の再現・説明を要求する指示** (エコー・転記・「なぜそう判断したか説明しろ」) は `reasoning_extraction` 拒否カテゴリを踏み、下位モデルへのフォールバックを増やす。**移行時に既存 skill / システムプロンプトを監査して削除する。** 推論の可視性が必要なら適応的思考の構造化 `thinking` ブロックを読み、実行中の表示は逐語 tool を使う
- 攻撃的サイバーセキュリティ / 生物・ライフサイエンス / 思考の抽出には安全性分類器が走り、無害な作業でも踏むことがある。`stop_reason: "refusal"` に対する下位モデルへのフォールバックを設計に含める

## まれな停止・自己縮小

- **早期停止**: 長いセッションの深い段階で、対応する tool 呼び出しなしにテキストだけの意図表明 (「これから X します」) で turn を終えることがある。「続けて」で足りるが、自律パイプラインではリマインダーを置く: 「自律動作中でユーザーはリアルタイムで見ておらず質問に答えられない。原依頼から導かれる可逆な行動は訊かずに進める。turn を終える前に最後の段落を見る。それが計画・分析・質問・次の手順・未実施の作業についての約束なら、今 tool 呼び出しで実行する」
- **コンテキスト残量への懸念**: 非常に長いセッションで、新セッションを提案したり要約引き継ぎを申し出たり自分の作業を削ったりする。**ハーネスが残トークンのカウントダウンを見せているときに最も出る** ので、可能なら表示しない。表示が必要なら「コンテキストは十分残っている。制限を理由に止まったり要約したり新セッションを提案したりしない」と安心させる

## スキャフォールディングの見直し

- **難易度範囲の最上位から始める。** 下位モデルに割り当てるより難しいタスクを渡し、スコープ定義と明確化の質問をさせてから実行させる
- **旧世代向けの skill は規範的すぎて品質を下げる。** 既定の性能のほうが良い箇所は、古い指示を削除する側に倒す
- 依頼だけでなく**理由**を渡す (「[誰] のための [大きなタスク] をやっていて、[出力で何ができるようになるか] が必要。その前提で: [依頼]」)

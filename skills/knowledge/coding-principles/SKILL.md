# coding-principles

コードを書く・編集するすべての場面で適用するコード行レベルの原則。設計・テスト・リリースなど上位の判断は engineering-judgment skill が担い、本 skill はコードそのものの規約のみ扱う。

## 命名

- 変数・概念・論点にはユビキタス言語 (意味が直接伝わるドメイン用語) を使う。α/β/L-α/S-1 等の記号は最初から使わない
- スコープが狭くても記号は禁止。「スコープが長くなったら置換」という事後対応は漏れが起きやすい
- 略号を使うなら省略前のフルネームを正本で先に定義し、文脈が確実な場合のみ短縮形を使う

## 実装指針

- 名前で意図を表現する
- 迷ったら可読性を優先する
- 症状ではなく根本原因を修正する。場当たり的回避策は禁止
- 暗黙のフォールバックは禁止。エラーは明示的に処理する — 対象は仕様化されない握り潰しや暗黙代入。仕様化・テストで固定した fail-open / fail-closed や DI seam の default (`x if x is not None else RealImpl()`) は本禁則の対象外
- boolean 引数は禁止。パラメータで振る舞いを分岐させない (production コード対象。test の parametrize 目的の keyword-only boolean は対象外)
- 安易なオプショナルは避ける。呼び出し側に意図を表現させる

## 構造設計

- KISS: 最もシンプルな解決策を選ぶ
- DRY: 同じ責務のコードは集約する
- SLAP: 関数内の文は同じ抽象レベルに保つ
- SRP: 1 クラス/モジュール、1 責務
- 複数モジュール間で同じ定数を必要とする場合、共通化またはどちらか一方への参照統一で、構造上に保証する。テスト assertion での一貫性検証のみに依存するな

原則同士が競合したら engineering-judgment skill の「原則の競合解決」(変更影響の局所化を最優先) に従う。

## 実装の意図をどこに込めるか

意図には 4 側面があり、それぞれ表現先が異なる。

| 意図の側面 | 表現先 |
|-----------|--------|
| 仕様 (WHAT) | テスト |
| 実現方法 (HOW) | コード自体 |
| 変更の動機・背景 (WHY: 変更単位) | コミットログ |
| 非自明な選択の理由 (WHY: 実装単位) | コメント (コード内) |

非自明な制約・workaround の WHY はコード内コメントに書く (harness 側の no-comment 既定に優先する)。名前・シグネチャで自明な WHAT を docstring / コメントで反復しない。

歴史的経緯・変更履歴は本文に持たず ADR / git log へ委ねる (追記型の履歴表は並行編集の conflict 源にもなる)。コメントは「なくても成立するならノイズ」— 迷ったら削除に倒す。

## 成果物ごとの表現

同じ知識でも、成果物の役割によって書き方の規範は逆になる。

| 成果物 | 規範 |
|---|---|
| 公開用 README | 「何があるか」「どう使うか」だけ書く。作り手側の経緯・背景・内部事情は書かない |
| 正本 (canonical source) | 単体で完結させる。簡潔さより正確さと詳細を優先し、原典があれば URL を付ける |
| 蒸留版 (SKILL.md 等) | 判断に使える決定規則へ圧縮する。根拠は正本へのリンクで済ませる |

## 品質基準

- 「シニアエンジニアがレビューして承認するか?」を判断基準にする
- 文字数制約のある成果物 (字数上限のある PR 説明・commit 本文など) を書くときの文字数カウントは `wc -m` を使う (`wc -c` はバイト数。UTF-8 日本語は 3 バイト/文字となり過大評価になる)

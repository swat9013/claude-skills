# pr-quality

Google Engineering Practices (`review/` 配下) を「競合したらどう判断するか」の決定規則に蒸留したもの。**PR を書く側 (§2 小分け・§3 説明文)** と **レビューする側 (§4 8 次元・§5 手順)** の両視点を扱う。

エンジニアリング判断全般 (設計・実装・リリース) は engineering-judgment、テスト設計は test-strategy を参照する。本 skill はそのうち **PR というアーティファクトの品質** に特化した詳細版。

用語: 原典は変更単位を CL (changelist) と呼ぶ。本書では GitHub 文脈に合わせ PR と読み替える (両者は「レビュー対象の 1 変更単位」として等価)。

## メタ規則 (最優先)

1. **この基準は既定値であって絶対ではない**。プロジェクト規約・既存レビュー文化と衝突したら文脈側を優先し、乖離をユーザーに報告する (engineering-judgment と同じ免責)。
2. **レビューの主目的はコード健全性を継続的に向上させること** — かつ設計改善と知識共有の場 (engineering-judgment「協働」節)。個々の PR を完璧にすることではない。
3. **主観・好みより事実・データ・確立した原則を根拠にする**。スタイルはスタイルガイドが権威、設計は原則で議論する。「私はこう書く」は根拠にしない (原典: reviewer/standard.md, comments.md)。

## CL 分割戦略 (PR を書く側 / 原典: developer/small-cls.md)

- **1 PR = 1 つの自己完結した変更**。1 つの機能追加、または 1 つのバグ修正に対応させる。関連するテストコードは同じ PR に含める。
- **サイズの目安は ~100 行**。1000 行超はほぼ確実に大きすぎる。ただし行数は目安であって規則ではない (ファイル全体削除・自動生成物は大きくてもよい)。
- **小さい PR ほど**: レビューが速く・徹底し、バグ混入・rework が減り、merge/rollback が容易で、設計も良くなり、他者を block しにくい。分割コストより回収が大きい。
- **分割軸**: (1) ファイル/コンポーネント単位 (2) 水平層 (API 層・永続層など層ごと) (3) 垂直機能 (1 機能を縦に薄く)。文脈に合う軸を選ぶ。
- **リファクタリングと機能追加は必ず分離する**。振る舞いを変えない変更 (整形・リネーム・構造変更) と振る舞いを変える変更を 1 PR に混ぜない — レビュアーが「どれが本質的変更か」を切り分けられなくなる (engineering-judgment のリファクタリング分離と同一)。
- **テスト改善 PR は対象機能 PR より先に出す**。基盤テストを整えてから機能を載せると、機能 PR のレビューで挙動保証が効く。
  - **先行分離するのは「既存コードのテスト基盤改善」(それ自体が独立した 1 変更)** に限る。**新規機能に付随するテストは前掲のとおり機能と同じ PR に含める** — TDD で実装と同時に書くテストを別 PR に切り出さない。判断軸: **その PR の主眼が「既存の挙動保証を厚くすること」なら先行別 PR、「新しい挙動を足すこと」なら付随テストごと同一 PR**。
- **1 課題 = 1 branch で進める実行形態では、順序付き複数 PR 分割 (refactoring/テスト基盤を先行 PR → behavior change を後続 PR) を同一 branch 内の commit 粒度分離に縮約してよい**。独立して ship できる単位は別の変更単位へ切り出す。

## PR 説明文 (PR を書く側 / 原典: developer/cl-descriptions.md)

- **1 行目は命令形で「何を変えたか」を完結した要約にする** (例: `Delete the FizzBuzz RPC`)。次に空行、その後に本文。
- **本文に理由・背景・制約・アプローチ・既知の欠点・関連 issue リンクを書く**。レビュアーと将来の読者が「なぜこの変更か」を PR 単体で理解できる状態にする。
- **「Fix bug」「Update」等の情報量ゼロは NG**。何の bug をどう直したかが分からない 1 行は失格。
- **説明文は永続ドキュメント**として扱う。将来コードを追う人が最初に読む記録であり、コミット履歴に残り続ける。実装が変わったら submit 前に説明文も見直す。

## レビュアー基準 8 次元 (レビューする側 / 原典: reviewer/standard.md + looking-for.md)

**承認の判断基準**: **この PR がコード健全性を確実に向上させるなら、完璧でなくても承認する**。完璧を承認の条件にしない — 継続的改善が完璧より優先する。改善提案は残しつつ、blocking でないものは `Nit:` 等で非 blocking と明示する。

以下 8 次元で見る (**設計が最重要**):

1. **設計 (Design)** — 変更が既存コードとうまく統合するか、ここに置くのが適切か。最も重要な観点。
2. **機能 (Functionality)** — 意図どおり動くか、ユーザー (エンドユーザー + 将来の開発者) にとって良いか。エッジケース・並行性を確認する。
3. **複雑性 (Complexity)** — 必要以上に複雑でないか。将来の必要性を見越した過剰な一般化 (speculative generality) を疑う。もっと単純にできないか。
4. **テスト (Tests)** — 適切なテストが変更と同じ PR にあるか、正しく意味のあるテストか (詳細は test-strategy)。
5. **命名 (Naming)** — 対象を過不足なく表す明確な名前か。
6. **コメント (Comments)** — 必要かつ明確か。WHAT でなく WHY を説明しているか。
7. **スタイル (Style)** — スタイルガイドに従うか。ガイド外の好みは blocking にしない (`Nit:`)。
8. **ドキュメント (Documentation)** — 関連する README・設計ドキュメント等を同時更新しているか。

補助原則: 人が書いた**全行に目を通す**。個別行だけでなく PR **全体の文脈**で見る。良い点は**明示的に褒める** (知識共有としてのレビュー)。

## レビュー手順 (レビューする側 / 原典: reviewer/navigate.md)

1. **説明文を読み、変更全体が意味をなすか俯瞰する**。方向性が根本的に誤っていれば、詳細を見る前に即座にその旨を伝える (レビュアー・作者双方の時間を守る)。
2. **メインの変更を先に見る**。中心となるファイル・最大のロジックから入ると、残りの文脈が掴める。
3. **残りを文脈が通る順序で見る**。全行を確認しつつ、依存関係の理解しやすい順に追う。

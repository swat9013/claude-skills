# test-strategy

テスト設計・戦略の価値観を「競合したらどちらを選ぶか」の決定規則に蒸留したもの。engineering-judgment skill の「## テスト」節 (TDD・Testing Trophy・カバレッジ床) の詳細版。テスト以外のエンジニアリング判断 (設計・リリース・エラー処理等) は engineering-judgment を参照する。

## メタ規則 (最優先)

1. **この基準は既定値であって絶対ではない**。プロジェクト規約・既存テスト資産の方針と衝突したら文脈側を優先し、乖離をユーザーに報告する。
2. **テストは目的ではなく手段** — 設計フィードバックとリグレッション防御のためにある (t-wada の整理)。手段の目的化の兆候 (カバレッジ数値の最大化競争・実装詳細を写経しただけのテスト) を見つけたら黙って従わず指摘する。

## 良いテストの 4 本柱

テストの良し悪しは 4 特性で評価する (Khorikov『Unit Testing Principles, Practices, and Patterns』): リグレッション防御 / リファクタリング耐性 / 高速フィードバック / 保守性。

- **リファクタリング耐性だけは妥協不可**。他の 3 特性は程度のトレードオフが可能だが、これは二値 — 実装詳細に結合したテストは false positive (振る舞い不変のリファクタリングで壊れる) を量産し、テストスイート全体への信頼を破壊する。
- したがって**検査対象は観測可能な振る舞い (observable behavior) のみ**。内部メソッドの呼び出し順・private 状態・中間データ構造を assert しない。

## テストレベルの選択

- **受け入れ条件・ユースケースの振る舞いを検査する自動テスト (e2e・統合テスト) を最優先で書く**。ユースケースは受け入れ条件であり、自動テストに落とす (engineering-judgment「設計」節と同一原則)。
- 投資配分は Testing Trophy (Dodds — 標語は Rauch "Write tests. Not too many. Mostly integration.")。ソフトウェアの実際の使われ方に似たテストほど高い信頼を与える。
- **単体テストは複雑なドメインロジック (計算・条件分岐が集中する箇所) へ集中投資する**。委譲だけの glue code に単体テストを書かない — 統合テストが間接的にカバーする。
- e2e は主要ユースケースの happy path + 重要経路 (決済・認可・データ削除) の異常系に絞る。網羅は統合レベルで行う (e2e は実行コスト・flaky リスクが最も高い層)。

## カバレッジ・ミューテーションテスト

- **カバレッジは必ず計測する**。計測なしのテスト戦略は観測なしの運用と同じ — 議論の土台が存在しない。
- **カバレッジは負の指標として使う**: 低い = テスト不足の確定シグナル、高い ≠ テスト十分 (assertion のないテストでも数値は上がる — Khorikov)。数値の最大化を目標にしない。
- 数値は回帰下限 (floor) として運用する: 下げない基準であって上げる目標ではない。重要経路は床を高く設定する (engineering-judgment と同一)。
- **ミューテーションテストでテストスイートの実効性を検証する**。カバレッジは「コードが実行されたか」しか示せない。mutation score は「変異 (=人工バグ) を検出できるか」を示し、assertion の質を測れる唯一の自動指標。全面適用はコストが高いため、重要経路・ドメインロジックから優先適用する。

## テストダブル

- **mock を許すのは unmanaged dependency のみ** (Khorikov): 外部からも観測される out-of-process 依存 (外部 API・メール送信・message bus)。これらとの通信は観測可能な振る舞いの一部であり、通信自体を検証する意味がある。
- **managed dependency (自アプリのみが使う DB 等) は mock しない**。実物 (テスト用インスタンス・testcontainers) か fake を使う。DB との通信は実装詳細であり、mock するとリファクタリング耐性を失う。
- 時刻・乱数・環境変数は注入で制御する (引数 or 依存として渡す)。テスト内 sleep・実時刻依存は flaky の温床。
- **ドメインロジックの協調オブジェクトは実物を使う** (classical / Detroit 派 — Khorikov も同派)。mock だらけのテストは実装詳細への結合が進行している兆候。

## テスト保守・品質

- **flaky テストは検知したら即隔離し、修理するか削除する**。「再実行すれば通る」の放置はテストスイート全体への信頼を殺す — 信頼できないテストは無いより悪い。
- **テスト名は振る舞いの仕様として書く**: 「どういう状況で何をしたら何が起こるべきか」をドメインの語彙で。メソッド名の写経 (`test_calculate`) は書かない。
- 1 テスト 1 振る舞い。AAA (Arrange-Act-Assert) 構造を保ち、Act は原則 1 行。Assert が肥大するなら検査対象の粒度を疑う。
- **リファクタリング (振る舞い不変の変更) でテストが壊れたら、テスト側の設計不良を疑う**。原因はほぼ実装詳細への結合。プロダクトコードを歪めず、テストを観測可能な振る舞いベースに書き直す。
- テストコードにも deletability を適用する: 機能を消すときテストも一緒に消せる構造にする。テストコードの重複は本体コードより許容度を高くしてよい (DRY より DAMP — 各テストが単独で読めることが優先)。

## 根拠 (原典)

- Khorikov『Unit Testing Principles, Practices, and Patterns』— 4 本柱 / observable behavior / managed・unmanaged dependency の区別 / classical 派
- Dodds "The Testing Trophy" / Rauch "Write tests. Not too many. Mostly integration." — 投資配分
- Beck『Test-Driven Development: By Example』— TDD (開発リズムとしての規定は engineering-judgment 側)
- t-wada — テストは手段であり目的ではない、の整理

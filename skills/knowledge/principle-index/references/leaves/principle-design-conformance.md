# 変更を設計 doc に照らし、適合とずれを分けて見る (conformance / design drift)

設計 doc は人が決めた規範なので、変更を照らす正本にする。照らす変更は issue の指定・コードの差分・指示文のどれでもよく、どれにも同じ 2 つの検査を当てる。

## 2 つの検査と区分

| 検査 | 見るもの | 区分 |
|---|---|---|
| conformance (設計への適合) | 変更が、設計 doc が保証として書いた事項 (ユースケースの形なら成功保証・最低保証・Extensions など)・不変条件・境界に反していないか | 変更の側を直せば沿うなら、agent が直す。沿わせるのに設計 doc を変える必要があるなら、方針の変更として人へ返す |
| design drift (設計とのずれ) | 変更が、設計 doc の記述する構造 (境界・ユースケース・entity・多重度・状態機械など) を変えているのに、設計 doc が先に直っていないか | 方針の変更として人へ返す |

- 設計 doc への当てはめは、人が決めた規範の当てはめなので AFK 境界 (`principle-ai-delegation-boundary`) の内側にある。設計 doc を変えるのは人の決定なので、design drift を見つけても agent は設計 doc を書き換えて解消しない — 人が読んでいない文面が設計 doc に入り、設計 doc が実装の後追いの要約に落ちる
- 構造を変えたかは、差分と設計 doc を読んで決める。指摘には、反した・ずれた設計 doc の行を file:line で引く。設計 doc の形 (システム関連図・ユースケース・ドメインモデルの 3 点など) は問わない
- 設計 doc を先に直してから実装する規則そのものは `principle-design-derivation-order` が持つ。本原則は、その規則が守られたかを変更から確かめる検査の側を持つ
- 設計 doc と他の規範 (rules・決定記録・同じ path に当たる別の設計 doc など) が食い違ったら、`principle-norm-precedence` で裁く

## 差分が設計 doc を書き換えているとき

- 変更の発端 (issue 本文など、変更の仕様の源) がその設計 doc の変更を引いていれば、変更後の設計 doc を正本にして conformance を見る — 人が発端で読んで決めた変更なので
- 発端が引いていなければ (発端が無いときを含む)、方針の変更として人へ返す — 人がその文面を読んだかを、差分からは確かめられない

## 設計 doc の置き場の引き方

- 照らす設計 doc は、対象 repo の `docs/agents/domain.md` の節「設計 doc の置き場」が案内するものだけにする。規約の path (`docs/design/*/` など) や既定の名前では探さない — 宣言の外を探すと、置き場を決める repo の代わりに読み手が置き場を決めることになり、repo が宣言で置き場を入れ替えられなくなる
- 節が無いか、節が設計 doc を 1 つも案内しなければ、照らさずに進む。置き場の宣言は repo ごとに無いことが正常なので、止まる理由にしない
- 節の表の行は `置き場 | 適用範囲 | 索引` で (repo が先に書いた表は旧い列名 `縛る対象` のままのことがあるので、その列も同じ列として読む)、設計 doc を当てるのは、変更の path が適用範囲に当たる行だけ。適用範囲は path の glob に加えて glob で書けない除外の文 (「〜に登録の無いものは除く」など) を含みうるので、当たるかは除外の文まで含めて決める。適用範囲が空の行は、設計 doc の中身から当たるかを決める。索引はその置き場の入口になる file を名指し、空なら置き場の全体が入口になる
- 適用範囲が重なる path には、当たる行の設計 doc をすべて当てる

# 制約から構造を導出する

- **導出順序**: 制約 (ビジネス・チーム規模・非機能要件) → アーキテクチャ特性 (architecture characteristics — 影響度の高い -ilities のみ選抜する。Richards & Ford『Fundamentals of Software Architecture』) → 構造 → 手段 (ツール・skill 化・図示)。設計後に見つかった観点で制約を問い直すループを回す
- **手段は最後に決める**: 検討の入口では課題と目的だけを固定する。手段を先に置くと、その手段で解ける形に課題が切り直されて、解くべき課題が入れ替わる。検討結果を文書にするときも同じ順序で書き、手段は一例として置く
- **構造を変える前に、その構造の課題と目的を問い直す**: 既存の構造を足す・強める・置き換える判断は、その構造がどの対象 (entity・状態・境界・利用者の作業) のどんな課題を解き、何の目的を達成するために置かれたかを、設計文書・決定記録・規範に書かれた形で言い直してから下す — 構造が働いていても起きる問題は、構造の不足より課題設定か目的の誤りを示していることがあり、誤ったまま構造を変えると、導出順序の上流を飛ばして手段だけを積み替えることになる
  - 言い直した課題と目的が正しく、構造が足りないだけなら、構造を強めるか置き換える
  - 言い直した課題と目的が起きた問題と食い違うなら、誤りの所在と直し方の案を人に返し、人が課題設定 (設計文書・規範) を直してから構造を導き直す — 課題設定を変えるのは、目的や構造の方針そのものを変える判断に当たる (`principle-ai-delegation-boundary`。設計文書については `principle-design-conformance`)
  - 目的がどこにも書かれていなければ推測で補わず、人に返す — 書かれていない目的を決めるのは repo の目的を決める判断に当たる
- **決定の遅延**: 不可逆な決定は last responsible moment (Poppendieck『Lean Software Development』) まで遅らせる。ただし遅らせすぎて「未決定」がデフォルトの決定になるのは失敗
- **ドメインモデルはユースケースから導き、構造は最小から始めて実装の知見で還流する** (Clean Architecture / DDD 系譜のユースケース駆動)。モデルを先に置くとユースケースがモデルに合わせて切り直され、構造を先に作り込むと、実装で得た知見を構造へ返すには作り込んだ部分を崩すことになる。ユースケースを受け入れ条件として自動テストへ落とすことは `principle-test-level-allocation` が扱う
- **設計を変える変更 (ドメインモデルの概念・関係、または記録済みの決定を変える変更) は、設計文書を先に更新してから実装する**。実装を先に変えると、設計文書は導出元ではなく実装の後追いになる。実装中に設計変更が要ると分かったときも、実装を続ける前に設計文書へ還流する。スパイク・prototype と明示した探索目的の使い捨ては対象外で、本流に採用する時点で設計文書へ還流する — 探索は設計を見つけるための手段なので、先に直せる設計文書がまだ無い
- **最適化目標の既定は、少ない人手で運用できること**。制約が別の目標 (性能・規模など) を挙げたら、そちらを優先する。どの目標でも、回復不能な構造の回避を局所最適より先に置く — 局所最適は後から取り戻せるが、回復不能な構造は取り戻せない

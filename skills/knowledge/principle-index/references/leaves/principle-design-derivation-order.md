# 制約から構造を導出する

- **導出順序**: 制約 (ビジネス・チーム規模・非機能要件) → アーキテクチャ特性 (architecture characteristics — 影響度の高い -ilities のみ選抜する。Richards & Ford『Fundamentals of Software Architecture』) → 構造 → 手段 (ツール・skill 化・図示)。設計後に見つかった観点で制約を問い直すループを回す
- **手段は最後に決める**: 検討の入口では課題と目的だけを固定する。手段を先に置くと、その手段で解ける形に課題が切り直されて、解くべき課題が入れ替わる。検討結果を文書にするときも同じ順序で書き、手段は一例として置く
- **仕様は直交する規則で持つ**: 条件の羅列が出てきたら、その羅列を仕様にせず、羅列を生んでいる直交する (互いに独立な) 規則を見出してそちらを仕様にする。表に出る個々の条件は規則の組み合わせの 1 つで、導出元にあたるのは規則のほう。組み合わせごとに条件を書くと規則が 1 つ増えるたびに条件が掛け算で増え、書き漏れた組み合わせが未定義のまま残る。個々のケースは仕様ではなく規則の検証 (受け入れ条件・テスト) に使う。判定は「新しいケースが来たとき、条件を 1 行足さずに既存の規則の組み合わせで説明できるか」。そもそも条件を減らして 1 本にできないかは `principle-structure-simplicity` で先に見る
- **決定の遅延**: 不可逆な決定は last responsible moment (Poppendieck『Lean Software Development』) まで遅らせる。ただし遅らせすぎて「未決定」がデフォルトの決定になるのは失敗
- **進め方**: ユースケース洗い出し → ドメインモデル抽出 → 最小構造で実装 → 実装知見をユースケース・モデル・構造へ還流する。ユースケースは受け入れ条件であり、自動テストに落とす (Clean Architecture / DDD 系譜のユースケース駆動)
- **最適化目標**: 少人数で効率よく運用できるシステム。回復不能な構造 (最悪) の回避が、局所最適より先

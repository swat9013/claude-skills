# 差分も土台も短命に保つ (trunk-based development)

- **短命ブランチ (1-2 日) で小さく統合する** (scaled trunk-based development — trunkbaseddevelopment.com)。長命 feature branch を作らないのを既定にする (= 作った差分をどれだけ短命に保つか)
- **計画した移行の branch は 1-2 日を超えてよく、途中の破損は branch の中に限る**。計画した移行とは、着手の前に、段階の境界・破損を許す範囲・境界ごとの検査・完了時の全体の検査を書いた計画 (issue か、複数の issue を束ねる親 issue) があり、その計画を人が書いたか承認した書き換え・移行を指す — 主幹を守る既定を緩めてよいかは、計画を読んだ人が決める (`principle-ai-delegation-boundary`)。自律実行中に計画した移行が要ると見たら、既定のまま進められる範囲だけを進め、計画の案を人へ返す。途中の状態を動かし続けるために小さく統合すると、移行の間だけ要る互換層を足すことになり、移行の後も残る。途中の状態を保つための互換層は足さない (利用者のために互換を残すかは `principle-deletability`)。主幹には段階の境界の検査を通った状態だけを入れる — 主幹は利用者とほかの作業が読む場所で、壊れた状態は取り消すまで読む側を壊す。計画が無ければ上の既定 (小さく統合) のままにする — 変更が大きいだけなら小さく切れることが多く、破損を許す理由にならない。この branch でも土台は次項のとおり主幹の最新に保ち、段階の境界の検査は最新を取り込んでから通す — 古い土台で通った検査は、主幹へ入れた後の状態を保証しない
- **土台は常に主幹の最新にする**: 着手時に最新を取り込み、安定版を狙って取り込む時期をずらさない。最新で問題が出たらその場で直す (見送って古い土台に留まらない)。fetch / pull のコストは払う前提で組む (= 土台をどれだけ新しく保つか)
- **Ship small, ship often**。出す間隔を空けず、1 回に 1 つの変更単位を出す。溜めると差分が長命になり、統合時の衝突が増える (変更単位の切り方は `principle-self-contained-change`)
- **展開は段階的 (canary release / feature toggle) が理想**。低リスクシステム (社内ツール等) は continuous deployment でよい。feature toggle は短命に保つ (Hodgson — long-lived toggle は複雑化リスク)

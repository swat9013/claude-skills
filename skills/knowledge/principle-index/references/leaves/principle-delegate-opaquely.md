# 委譲先は呼び出し口だけで扱う

- **依存してよいのは委譲先の呼び出し口だけ** (Law of Demeter — Lieberherr & Holland 1989 / information hiding — Parnas 1972)。呼び出し口とは、委譲先が入口として公開した名前・path・引数・呼び出し方と、その返り値・成否を指す。委譲先の内部手順・内部コスト・委譲先が抱える依存物とその失敗モードは、呼び出し側のコードにも文面にも書かず委譲先の側に置く
- **呼び出し側が自分の言葉で持つのは、委譲先が報告できないことだけ**。直接の委譲先が不在 (未導入・不通) なら呼び出し側が検知して loud に止め、復旧手順を案内する。委譲先が動いている間の不具合の検知・案内・復旧は委譲先が持ち、呼び出し側は成否を受け取る。ほかに持つのは自分自身の保証 (例:「人間承認を得ていない write はゼロ」) と、自分がやらないことの宣言
- **判定は「委譲先の内部が変わったとき呼び出し側を直すか」**。直すなら内部知識を転記している (呼び出し口は内部ではないので、それを書くのは転記に当たらない)。転記は integration strength が最も強い intrusive coupling で、委譲先の改訂が呼び出し側を黙って腐らせる (結合の強さそのものを評価するときは `principle-balance-coupling` を読む)
- **skill が他 skill を invoke する経路・tool を呼ぶ経路も、module 間の呼び出しとして同じ線で見る**。委譲先が内部で依存する plugin 名・委譲先が内部で起動する subagent の数は委譲先の本文に置く

委譲してよい範囲と人間へ返す境界は `principle-ai-delegation-boundary` が扱う。本原則は**委譲先の何を呼び出し側に持たせるか**を決める。

# 捨てやすさを拡張しやすさより優先する

- **deletability を重視する** (tef "Write code that is easy to delete, not easy to extend")。AI で機能実装コストは下がったため、「拡張しやすさ」より「変更影響が波及しない・機能単位で捨てられる」構造を選ぶ。※12-factor の Disposability (プロセスの起動終了) とは別概念
- **撤去は実績を起点に決める**: 導入したものは利用実績 (呼び出し回数・使用実績) を定期的に観測し、使われていないものを削除する側にも追加と同じ頻度で回す。撤去の根拠は「不要そう」という印象ではなく実測値 (= いつ捨てると決めるか)
- **更新を強い続けるものは、使われていても撤去側へ倒す**: 撤去判断は使用実績と保守コストの 2 軸で見る。保守コストの観測値は「本体を変えるたびに追随更新を要求してきた回数」。一時的な目的で作った生成物 (移行用の固定値・スナップショット) がこれに当たるなら、撤去か生成への置き換えを選ぶ
- **導入は価値の立つ項目だけに絞る**: 全部入りの既定をそのまま抱えず、価値を言える少数から始めて必要になってから足す。導入した項目はその時点から撤去判断の対象に入る
- **捨てるときは歴史を残す**: 撤退・移行を決めたら削除して終わりにせず、戻れる記録 (ADR / アーカイブ) と再検討トリガー条件 (どうなったら戻すか) を残す (= 捨てると決めた後に何を残すか)

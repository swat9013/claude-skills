# 完了を宣言する前に実物で確かめる

- **検証対象は実物にする**。ビルドが通った・タイムスタンプが新しい・キャッシュにある、といった代理指標で完了を判断しない
- **外部ツール・サービスの仕様 (用語・挙動) に依存する記述は、一次情報 (公式ドキュメント、または実際に動かして観測した挙動) で裏取りしてから使う**。記憶や推測で書いた仕様は代理指標と同じで、実物を確かめたことにならない
- **経路を端から端まで通す**: 実装した機能を実際の使われ方どおりに動かし、入力から出力までデータが流れることを確かめる
- **合否は、実物を見た者が主張する**。作った本人の報告は合否の根拠にしない (報告は意図であって結果ではない)。検証は作った者とは別の文脈へ委ねてよく、検証した側は、本流が確かめ直せる証拠 (実行したコマンドと出力、`file:line`) を添えて返す — 証拠の無い合否は、本流にとって自己申告と同じになる
- **検査が落ちたら、系より先に観測の方法を疑う**: 落ちた検査は、系の欠陥ではなく観測の誤り (見ている対象・手順・期待値の誤り) を映していることがある。観測が正しいと確かめてから、系の欠陥として扱い、どの層を直すかは `principle-root-cause-and-hierarchy-of-controls` に従う。通っていた検査が、系を変えた直後に落ちたときは、系を先に疑う — 変えたものが最も疑わしい
- **他者が再実行できる検証は、一度きりの目視より強い**。検証を script にするかは `principle-when-to-automate` に従う

合格線そのものの判定は `principle-review-ready-bar` が扱う。本原則は**合格や仕様を主張する前に何を根拠に置くか**を決める。

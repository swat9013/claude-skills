# 完了を宣言する前に実物で確かめる

- **検証対象は実物にする**。ビルドが通った・タイムスタンプが新しい・キャッシュにある、といった代理指標で完了を判断しない
- **外部ツール・サービスの仕様 (用語・挙動) に依存する記述は、一次情報 (公式ドキュメント、または実際に動かして観測した挙動) で裏取りしてから使う**。記憶や推測で書いた仕様は代理指標と同じで、実物を確かめたことにならない
- **経路を端から端まで通す**: 実装した機能を実際の使われ方どおりに動かし、入力から出力までデータが流れることを確かめる
- **委譲した作業は成果物で受け取る**。エージェントの報告文ではなく、生成された差分・ファイルの中身・実行時の挙動を自分で見る (報告は意図であって結果ではない)
- **観測方法を疑ってよいのは条件付き**: その検証経路を一度も通したことがない、または系側に変更が無いのに落ちた場合に限り、観測側を 1 度だけ確かめる。それ以外は系の欠陥として扱う (`principle-root-cause-and-hierarchy-of-controls`)
- **同じ検証を繰り返すなら決定的な script にする**。他者が再実行できる形は一度きりの目視より強い (自動化する時期の判断は `principle-when-to-automate`)

合格線そのものの判定は `principle-review-ready-bar` が扱う。本原則は**合格や仕様を主張する前に何を根拠に置くか**を決める。

# 書かずに済むコードは書かない

- **作るのは依頼が求めるものだけにする** (YAGNI): 書いたコードは読まれ、保守され、壊れる対象になる。依頼に無い機能・オプション・設定項目・拡張点と、1 回しか使わない操作のための helper や抽象層は作らない — 使われない部品も保守と読解のコストを毎回負わせる
- **既にあるもので満たす**: 依頼が求める処理をそのまま担える同じ codebase の処理、標準ライブラリとプラットフォーム、導入済みの依存があれば、新しく書くよりそれを呼ぶ — 既にあるものは読まれ、試され、保守されている。複数で満たせるなら、同じ codebase の部品、標準ライブラリとプラットフォーム、導入済みの依存の順に選ぶ — 読み手が既に知っている語彙ほど読む負荷が小さい。既存の処理を広げて使うのは、依頼が求める処理と同じ知識 (DRY の意味で、同じ理由で変わるもの) を持つときだけにする — 異なる理由で変わる処理を広げると、片方の変更がもう片方へ波及する結合になる (結合の扱いは `principle-state-coupling-complexity-code`)。新しい依存を足すか自前で書くかは `principle-build-vs-buy` で決める
- **最小は読み手が追う部品の数で測る**: 行数や文字数では測らない。一目で読めない 1 行は、行数が少なくても最小に数えない — 詰め込んだ式は読む負荷を増やす
- **最小にするのは解法で、変更の範囲ではない**: 変えた箇所の呼び出し側・テスト・設定は同じ変更で追従させる — 追従を後回しにすると、変更は小さくても壊れた状態が残る。範囲の外で見つけた欠陥の扱いは repo の規範に従う
- **最小にしても残すもの**: 信頼境界での入力の検証、データを失わないためのエラー処理、セキュリティ、アクセシビリティ、テストを書く対象のテスト — 省くと失敗するまで見えず、後から足すほど高くつく。テストを書くか・どれだけ厚くするかは `principle-test-thickness-by-property` が決める。境界の内側で起こり得ない状況の検証は足さない (`principle-validate-at-boundaries`)
- **省いた判断は読み手に見える形で残す**: 要りそうだと見て作らなかったものと確かめていないことは、黙って省かずに報告へ出す — 最小に止めた判断は差分には現れないので、読み手が検められるのは報告だけになる

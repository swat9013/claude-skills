# 状態 > 結合 > 複雑性 > コード量の順に案を比べる

ある箇所の変更が他へ波及しない構造を選ぶ (coupling / cohesion — Stevens, Myers & Constantine 1974)。DRY・SOLID・KISS と競合したら波及を抑える側を選ぶ。

案を比べるときは、次の 4 基準をこの優先順位で見る。まず状態の増減で比べ、差が無ければ結合、次に複雑性、最後にコード量で比べる。上位の基準が減るなら、下位の基準が増えることを受け入れる。

1. **状態**: 検討している範囲が抱える可変状態 (field・フラグ・キャッシュ・インメモリの queue)。ステートレスな処理は逐次・並列・分散のどれでも同じに動き、状態を再現するセットアップがほとんど要らないのでテストしやすく、最も推論しやすい。状態を持つ処理は、変更の前提が過去の操作の履歴に散らばるので、変更の影響範囲を 1 箇所から読み切れない。状態が減るなら結合が増えてもよい (例: コンポーネント内のインメモリなジョブキューを、専用のキュー管理コンポーネントへ任せる。状態は外へ移り、手元の状態が減る)
2. **結合**: 結合が減るなら構造が複雑になってもよい
3. **複雑性**: 状態と結合を除いた、読み手の認知負荷 (分岐・循環的複雑度など)。複雑性が減るなら、似ているだけのコード (異なる理由で変わるコード) を複製してよい。同じ知識の複製は 1 つの変更を複数箇所へ波及させる結合なので、2 の結合として数える (複製しない)
4. **コード量**: コードの総量と変更の差分行数。最後に削る。似ているだけのコードの重複の排除は、状態・結合・複雑性のどれも増やさないときだけ行う

- **上位を減らすための分割も、変更が触る箇所を増やすなら採らない**。1 つの変更が分けた先の複数箇所へ同時に届くなら、結合は減っていない。過剰分割 (分散モノリス・早すぎる抽象化) はこの原則の違反
- 4 基準のうち最も目に付くのはコード量、特に変更の差分行数なので、判断はそこへ引き寄せられる。差分の小さい案ほど、状態と結合を増やしていないかを先に確かめる。例: 既存モデルに 2 つ目のユースケースを持たせる案は差分が小さいが、同じモデル内で気にする状態が増える。ユースケースごとにモデルを分ける案はコード量と複雑性が増えるが、状態と結合が減るので、この比較では後者を選ぶ

# 剪定してよいのは限界価値ゼロを確認したときだけ

テストの費用対効果は**限界価値 ÷ 生涯コスト**で評価する。問うのは「良いテストか」ではなく「このテストが消えたときスイート全体の検出力が下がるか」— 1 本ずつは良いテストでも、重複していれば限界価値はゼロ。

- **限界価値 (分子) = そのテストだけが提供するリグレッション検出力**。代理指標は「そのテストだけが殺す変異 (mutation)」「そのテストだけが踏む covered 文」。設計フィードバックの価値は作成時に一度きり支払われるもので、保守フェーズの剪定判断では分子に入れない
- **生涯コスト (分母) = 実行コスト (実行時間 × 実行回数) + 保守コスト (false positive 対応 × 変更頻度) + 理解コスト**。作成コストは埋没費用 — 剪定判断では無視する
- **分母の支配項は実装詳細への結合**。false positive を量産するテストは変更のたびにコストを払わせ、分母が変更頻度に比例して発散する (`principle-observable-behavior` の「リファクタリング耐性だけは妥協不可」はこの帰結)
- **剪定してよいのは限界価値ゼロを確認したときだけ**: ① 消しても covered 文数が減らない ② 消しても mutation score が下がらない (mutation を測っていないプロジェクトでは、そのテストが単独で守る境界値・分類の優先順・語彙の終端が無いことを確認する) ③ 同じ振る舞いをより観測点に近いテスト (公開 API の返却値・exit code・外部境界へ出た命令) が検査している — の 3 条件が揃ったとき。確定後の処置は削除だけでなく統合 (より観測点に近い 1 本へ畳む) でもよい
- **候補は限界価値ゼロの典型パターンから探す**: 実装のコピー (期待値を実装と同じロジックで導出していて、実装のバグごと合格する)、mock の自己検証 (mock に設定した応答をそのまま assert していて、検査対象がテスト自身)、型システムやライブラリが既に保証する性質の再確認 (null 拒否・enum 網羅など、compile や依存先のテストが既に落とすもの)、同値クラス内の過剰なケース分け (境界値でも分類の優先順でもないケースの列挙)。パターン合致は候補化までで、確定は限界価値ゼロの 3 条件で行う
- **総量の適正は LOC 比・ケース数・カバレッジ % では判定できない**。基準は信頼水準 (Beck): 到達すべき confidence を固定し、そこへ最小のテストで到達する。「多すぎるか」は数ではなく、限界価値ゼロのテストの濃度で測る

新規にどこへテストを書くかの投資判断は `principle-test-level-allocation` が扱う。

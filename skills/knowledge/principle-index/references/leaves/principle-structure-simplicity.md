# 構造はシンプルに保つ

- KISS: 最もシンプルな解決策を選ぶ — 読み手が追う部品と分岐が少ないほど、変更の影響を読み切れる
- 稀にしか起きない事象 (操作の取り消し・やり直し・個別の設定作業) への対処を仕組みに組み込むと仕組みが複雑になるなら、運用での吸収 (作り直す・その都度手で行う) を許して仕組みを簡素に保つ。稀な事象への対処を常設すると、その複雑さを毎回の変更で抱え続ける。再実行・再起動のたびに起きうる残骸の片付けはこの対象に含めず、`principle-idempotent-operations` に従う
- DRY: 同じ知識 (同じ理由で変わるもの) は 1 箇所に集約する。対象は知識でありコード行ではない (Hunt & Thomas『The Pragmatic Programmer』)。似ているだけのコード (異なる理由で変わるもの) の重複を排除するかは `principle-state-coupling-complexity-code` に従う。複数モジュールが同じ理由で変わる値 (同じ知識) を要るなら、共通化か参照の統一で構造上に保証し、テストの一致検証だけに頼らない — テストは食い違いを後から見つけるだけで、2 か所を直す手間と直し漏れは残る。互いを import も参照もできない置き場 (別々に配布される package のコードや設定など) だけは、構造で保証する手段が無いので、複製して一致検証 (test や gate) で守り、2 か所を直す手間を受け入れる
- SLAP: 関数内の文は同じ抽象レベルに保つ — 方針と細部が混ざると、読み手は細部を読み飛ばせず方針を見失う
- SRP: 1 クラス/モジュールは 1 つの変更理由だけを持つ — 無関係な理由の変更が同じ場所に集まると、片方の変更がもう片方を壊す

この leaf の原則同士 (共通化する DRY と、部品を増やさない KISS など) が競合したら `principle-state-coupling-complexity-code` に従う。

# 成果物ごとに書き方の規範は逆になる

同じ知識でも、成果物の役割によって書き方の規範は逆になる。

| 成果物 | 規範 |
|---|---|
| 公開用 README | 「何があるか」「どう使うか」だけ書く。作り手側の経緯・背景・内部事情は書かない |
| 正本 (canonical source) | 単体で完結させる。簡潔さより正確さと詳細を優先し、原典があれば URL を付ける |
| 蒸留版 (SKILL.md 等) | 判断に使える決定規則へ圧縮し、根拠 (他 skill・調査レポート・原則 leaf の内容) は同文の複製ではなく圧縮した形で本文に内包する。配布先で単体で読める形にし、参照先の改訂に追随しなくて済むようにする。残してよい外向き参照は、双方の本文で対にした蒸留元 / 詳細版と、手順が実際に Read / invoke する呼び出し先。原典の URL は付けてよいが、片方向の名指しと読み手が真偽を確かめられない外部参照 (特定ファイル番号・版へのピン留め) は載せない |
| 説明文書 (spec / plan / PR 説明文 / issue 本文) | 最終設計を最初から計画したものとして全面的に書く。読者は作成に至った会話の経緯を一切知らない新規参加者とし、経緯を知らないと意味が通じない文は残さない。PR 説明文にしか掛からない節構成・記載項目はこの leaf では扱わず、呼び出し元のフローに委ねる |
| 開発フロー文書 (CONTRIBUTING.md) | 人間向けと AI エージェント向けで文書を分けず、1 本を両者が読む。常時読まれる指示書や README からは参照にする |
| 実行時に読まれる指示書 (エージェント向け規約・手順書) | 実行時に必要な情報だけを書く。判定は「その記述が無いと実行結果が変わるか」。作成の経緯・改訂時の判断材料は別文書へ分け、常時ルールと各資料へのインデックスだけを残して高シグナルに保つ |

上の表は役割ごとに逆転する規範で、以下はどの成果物にも共通で掛かる。

- **読者層を先に決めてから書く**。判定は「想定読者が知らない用語を使うたびに、定義か具体例を添えているか」。前提知識を持たない層 (非エンジニア・その領域の初学者) が読者なら、概念を具体例で先に立てる
- **同じ知識は文書成果物の間で正本を 1 つに決め、他からは参照にする** (対象は文書に書かれた同文で、コードの共通化と配布物の前提宣言は別線)。複数の成果物へ同文を置くと、更新が片側にだけ入って黙って食い違う。新しい正本を立てたときは、そこへ移った記述を旧側から削除して参照に置き換えるところまでを 1 回の作業に含める
- 文字数制約のある成果物 (字数上限のある PR 説明・commit 本文など) を書くときの文字数カウントは `wc -m` を使う (`wc -c` はバイト数。UTF-8 日本語は 3 バイト/文字となり過大評価になる)

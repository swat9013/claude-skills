# 原則 leaf の索引

## 読み方

## leaf 一覧

- **principle-ai-delegation-boundary** — AI エージェントへ自律実行を委譲する範囲を決めるとき、人間へ返す境界を決めるとき、自律実行中に人へ問うか自分で判断して進むか迷ったときに適用する。委譲は AFK 境界で切り、人間に返すときは提示と引き渡しの形式まで決める。
- **principle-artifact-register** — README・正本・蒸留版・設計 doc / spec / plan / PR 説明文 / issue 本文・開発フロー文書 (CONTRIBUTING.md)・エージェント向け指示書といった文書を書くとき、記述を別文書へ移して正本を立て直すとき、字数の上限がある成果物の字数を数えるときに適用する。成果物の役割ごとに規範が逆になり、読者と正本の決め方はどの成果物にも共通で掛かる。
- **principle-balance-coupling** — モジュール / サービス境界の結合を評価するとき、境界を分割するか統合するか判断するときに適用する。integration strength / distance / volatility の 3 次元。
- **principle-blast-radius** — AI エージェントや自動実行に与える許可と禁止 (permission・sandbox・資格情報の権限) を設計するとき、拒否が頻発する制御を見直すときに適用する。禁止は副作用の有無で切り、権限範囲と隔離で被害の及ぶ範囲を限る。
- **principle-build-vs-buy** — 自前実装と既製品が拮抗したとき、言語・フレームワーク・ライブラリを選定するとき、既製品を fork して維持するか・確立した仕組みを自前へ置き換えるか決めるときに適用する。既製品を既定に置き、選定軸をテスト容易性・可読性・構築の簡単さと上流への追従コストで切る。
- **principle-collective-ownership** — コードの所有範囲・レビューの目的を決めるときに適用する。特定個人しか触れないコードを作らず、レビューは設計改善と知識共有の場にする。
- **principle-context-budget** — 大きな出力・長いファイル・委譲や参照の設計で context を消費するときに適用する。context は再生しない有限資源として配分する。
- **principle-coverage-as-floor** — カバレッジやミューテーションスコアを運用するとき、数値目標や閾値を決めるときに適用する。カバレッジは負の指標かつ回帰下限。
- **principle-debt-quadrant** — 品質と速度が競合したとき、技術的負債を作るか・いつ返すか決めるとき、根本原因を直さず回避策で進めるか決めるときに適用する。Technical Debt Quadrant による許容判定。
- **principle-delegate-opaquely** — 他の skill / module / service へ処理を委譲する側を書くとき、委譲先の前提・失敗・コストを呼び出し側でどう扱うか決めるときに適用する。呼び出し側が持つのは呼び出し口と自分自身の保証だけ。
- **principle-deletability** — 拡張しやすさと捨てやすさが競合したとき、機能・仕組みを撤去するか決めるとき、撤去した後に何を残すか決めるとき、導入する項目を絞るとき、形式・名前・URL を置き換えて互換層を残すか決めるときに適用する。撤去の起点は使用実績と保守コスト、置き換えは互換なしが既定、撤去後に残すのは戻れる記録。
- **principle-design-conformance** — issue の指定・コードの差分・指示文の変更を設計 doc に照らすとき、変更が設計 doc に反するか・設計 doc より先に構造を変えているかを判定するとき、照らす設計 doc を探すときに適用する。conformance と design drift の 2 つの検査、見つけた食い違いを直すか人へ返すかの区分、差分が設計 doc を書き換えるときの扱い、設計 doc の置き場の引き方。
- **principle-design-derivation-order** — アーキテクチャや構造を新しく決めるとき、既存の構造を足す・強める・置き換えるとき、不可逆な決定を今下すか遅らせるか迷ったとき、手段 (ツール・図示など) を課題より先に決めたくなったとき、設計を変える変更を実装するとき、最適化目標を選ぶときに適用する。制約 → アーキテクチャ特性 → 構造 → 手段の導出順序と、構造を変える前にその構造の課題と目的を問い直す規則、既定の最適化目標 (少ない人手で運用できること)、設計変更では設計文書を実装より先に直す規則。
- **principle-fail-loudly** — エラー処理・例外・フォールバック・縮退の挙動を書くときに適用する。失敗を即座に可視化する原則。
- **principle-idempotent-operations** — 再実行・再起動・リトライが起こりうる処理 (コマンド・ライフサイクル・処理ループ) を設計するときに適用する。前回の残骸があっても同じ終状態へ収束させる。
- **principle-intent-placement** — コメントや docstring を書くか迷うとき、変更の意図や設計判断の理由をどこに残すか決めるときに適用する。意図の側面 (仕様 / 実現方法 / 変更の動機 / 非自明な選択の理由 / 設計判断の理由) ごとに表現先を決める。
- **principle-intention-revealing-names** — 変数・関数・型・概念・論点・用語に名前を付けるとき、記号や略号で済ませたくなったとき、語を新しく作りたくなったときに適用する。既に定着した語 (leading word) を先に探し、無いときだけ意図を言い当てる語を作る。
- **principle-isolate-shared-writes** — 並行する書き手が同じ書き込み先 (ファイル・キー・状態オブジェクト) へ触れうる設計をするときに適用する。共有をまず解消し、残った共有だけを構造で直列化する。
- **principle-least-code** — コード・設定・script を書く・直すときに、どこまで作るかを決める場面で適用する。書いたコードは読まれ保守され壊れる対象になるので最小の解法で依頼を満たし、変更の範囲の追従と安全のための処理は削らない原則。
- **principle-log-design** — log・監査記録・実行痕跡を新しく書き出す処理を設計するとき、既存の log に項目を足すか判断するとき、log の書式・置き場・保持を決めるときに適用する。行の自己完結・書式・書き先・正常痕跡・秘匿・保持の判断規則。
- **principle-mechanism-not-policy** — 他の project へ配布されるもの (skill / CLI / library / template) の本文・手順・description を書くとき、配布物の振る舞いを実行環境によって変えたくなったとき、複数の実行環境で動かす仕組みが OS 固有機能に頼るか決めるときに適用する。配るのは仕組みだけで、運用方針は実行 project に委ね、環境差は共通 IF で吸収し、観測できない環境の事実では分岐しない。
- **principle-norm-precedence** — 2 つの書かれた規範 (rules・設計 doc・決定記録・指示文など) が同じ指定に食い違う向きを出し、どちらに従うかを決めるときに適用する。適用範囲を絞った規範が一般の規範に勝ち、決定記録どうしは日付の新しい方が勝つ優先順位と、優先順位で決まらない衝突を人へ返す規則。
- **principle-observable-behavior** — テストの検査対象と期待値の導き方を決めるとき、振る舞い不変のリファクタリングでテストが壊れたときに適用する。リファクタリング耐性は妥協不可。
- **principle-operability-first** — 運用性 (可観測性・デプロイ容易性) を設計するとき、監視と observability の投資順序を決めるとき、信頼性の余力をどう使うか決めるときに適用する。作った者が運用する前提で初期設計に運用性を組み込む。
- **principle-orthogonal-rules** — ルール・規範文・仕様に例外や条件分けを足したくなったとき、条件の羅列をそのまま仕様にしそうになったときに適用する。まず条件を減らして 1 本にし、残る条件は直交する規則へ畳む。
- **principle-quarantine-flaky** — 再実行すると結果が変わるテスト (flaky) を検知したときに適用する。放置せず隔離して修理か削除に倒す。
- **principle-review-ready-bar** — 変更を完了と宣言する前、レビューへ出す前に適用する。品質の合格線を判定する原則。
- **principle-risk-based-security** — セキュリティ検査をどの工程に置くか、検査を CI と hook のどちらで走らせるか、防御にどれだけ投資するか決めるときに適用する。検査は前倒しでローカル hook を起点に、投資は資産価値と脅威モデルで配分する。
- **principle-root-cause-and-hierarchy-of-controls** — バグを直すとき・デバッグするとき、計画・設計で問題への対処案を推奨するとき、繰り返す問題の共通原因を探すときに、修正や対処をどこに当てるか決める場面で適用する。問題を events / patterns / structures / mental models の 4 層 (iceberg model) で捉えて直す層を選び、修正の到達点を症状ではなく根本原因の側に置き、再発しうる問題は人の注意より構造で防ぐ側を選ぶ段の序列。
- **principle-self-contained-change** — 差分を PR / commit に切り分けるとき、レビューへ出す単位を決めるとき、作業中に本題外の変更を見つけたときに適用する。1 つの変更単位 (CL) には自己完結した 1 つの目的だけを載せる。
- **principle-short-lived-integration** — branch の寿命・リリースの頻度・展開方法を決めるとき、作業の土台をいつ最新化するか決めるときに適用する。差分も土台も短命に保つ側へ倒す。
- **principle-signature-intent** — 関数・メソッドのシグネチャと引数を設計するとき、boolean 引数やオプショナル引数を足したくなったときに適用する。呼び出し側に意図を表現させる原則。
- **principle-state-coupling-complexity-code** — 設計・実装の案を比べるとき、設計原則同士が競合したとき (DRY と KISS、共通化と独立性のどちらを取るか) に適用する。変更影響の局所化を最優先に置き、状態 > 結合 > 複雑性 > コード量の順で案を比べる。
- **principle-structure-simplicity** — 関数・クラス・モジュールの構造を決めるとき、責務の置き場や共通化の有無で迷ったとき、稀にしか起きない操作ミスや個別作業への対処を仕組みに組み込むか迷ったときに適用する。KISS / DRY / SLAP / SRP の原則と、稀な事象は運用で吸収して仕組みを簡素に保つ規則。
- **principle-tdd-rhythm** — テストを書く対象の機能実装・バグ修正に着手するとき、テストを先に書くか後に書くか決めるときに適用する。開発リズムとしての TDD。
- **principle-test-as-spec** — 個々のテストを書くときに適用する。テスト名の付け方・AAA 構造の粒度・テストコード側の DRY をどこまで緩めるかを決める。
- **principle-test-double-boundary** — テストで依存を差し替えるとき (mock / stub / fake / 実物のどれを使うか)、時刻・乱数・環境変数を制御するときに適用する。mock を許す境界は unmanaged dependency だけ。
- **principle-test-level-allocation** — 新しくどのレベルにテストを書くか決めるとき (単体 / 統合 / e2e の配分)、ユースケースや受け入れ条件をテストに落とすときに適用する。Testing Trophy による投資配分。
- **principle-test-pruning** — 標準以上の厚さで守る対象の既存テストを削るか決めるとき、テストが多すぎる・保守コストが高いと感じたときに適用する。限界価値 ÷ 生涯コストの評価。
- **principle-test-thickness-by-property** — 対象ごとにテストを書くか、どれだけ厚くするか、薄く保つ対象のテストを何本残すかを決めるときに適用する。所有者・振る舞いの有無・決定的か推論的か・黙って壊れるか・被害の回復性・利用者の範囲で厚さを引く。
- **principle-validate-at-boundaries** — 入力検証・型の絞り込み・防御的なエラー処理をどこに置くか決めるときに適用する。検証は境界に集約し、内側では型を信頼する。
- **principle-verify-the-real-artifact** — 作業を完了と宣言する前、委譲した作業を受け取るとき、外部ツール・サービスの仕様に依存する記述を書くときに適用する。代理指標や自己申告や記憶ではなく、実物と一次情報で確かめる。
- **principle-when-to-automate** — 反復作業を自動化するか決めるとき、規約の遵守をどう守らせるか決めるとき、LLM 推論を script へ追い出すか判断するときに適用する。自動化は痛みの実測後、遵守は機械で保証する。

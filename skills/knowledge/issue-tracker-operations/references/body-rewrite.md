# issue 本文の書き換え

issue 本文を書き換え、旧本文を逐語で記録する手順。同じ issue を他の書き手 (別の triage セッション・無人の worker・人) が同時に触りうるので、書き戻す前と後に本文を確かめて競合を検知する。一時 file は作業ツリーの外に置く (置き場は呼び出し元が決め、決めていなければ `mktemp` で作る)。本書の手順の tracker 操作と file の比較は、1 コマンドずつ別の呼出で撃つ (1 コマンドに flag を併せるのは構わない) — `&&`・`;`・pipe でつないだコマンドは、書き込み先が作業ツリーの内側かを判定できない session に拒否され、拒否された呼出の分だけ確かめ直しが増える。コマンドは対象 repo の `docs/agents/issue-tracker.md` の CLI 規約に従い、規約が無ければ GitHub (`gh`) の綴りの例を tracker の綴りへ読み替える。

## 基準の保存

基準は、書き換え案の元にした取得の本文にする。呼び出し元が本文を先に保存していなければ、書き換え案を作る前に `gh issue view <N> -R <issue 置き場> --json body --jq .body` で本文を file に保存し、書き換え案はこの file の本文を元に作る。呼び出し元が先に保存した本文 (複数の issue を 1 回で取得した JSON の file など) から書き換え案を作ったときは、その issue の body を `jq -r` などのコマンドで file に切り出す — context から書き起こすと逐語が崩れ、比較で偽の競合が出る。この file が書き戻す直前の比較の基準になる。別の取得で読んだ本文を書き換え案の元にしない — 二つの取得の間に入った他の書き手の編集を、比較で検知できなくなる。

同じ issue を続けて書き換えるときは、前回の書き戻しの読み直しで一致を確かめた本文 (前回書いた file) を次の基準にする。読み直しより後に他の書き手が入れば、次の比較で検知される。

## open CL の確かめ

書き戻しの手順 1 に入る前に、issue を閉じる open CL が無いことを確かめる。issue を閉じる CL とは、closing keyword か tracker の閉じる関連で、その issue を閉じると宣言した CL を指す。そうした CL が open の間に本文を書き換えると、実装中の CL が拠った仕様と本文が食い違い、CL を読む人もどちらが正か決められない。issue を参照するだけの CL (閉じると宣言せずに番号を書いた CL。本文が前提とする規範を足す CL など) は数えない — 数えると、その CL が merge を待つ間、本文を書き換えられない。

次のどちらかに当たる CL を、issue を閉じる open CL とする。

- `gh issue view <N> -R <issue 置き場> --json closedByPullRequestsReferences` が返す各 CL のうち、`gh pr view <url> --json state` が open を返すもの
- `gh pr list -R <CL 置き場> --state open --search "<N> in:body" --limit 1000 --json number,body` が返す CL (返った件数が `--limit` に届いたら上げて引き直す — 超えた分は黙って打ち切られる) のうち、本文が closing keyword の直後にこの issue を書いたもの。closing keyword は tracker の語 (GitHub なら `close`・`closes`・`closed`・`fix`・`fixes`・`fixed`・`resolve`・`resolves`・`resolved`。大文字小文字と直後の `:` は問わない) で、issue の書き方は `<owner>/<repo>#<N>` か issue の URL で、CL 置き場と issue 置き場が同じなら `#<N>` も含む (どれも番号の直後が数字でないもの)。GitHub は既定 branch 以外へ向かう CL の closing keyword を閉じる関連として張らないので、積み重ねた CL はこちらでしか見つからない

当たる CL があれば書き戻さずに止める (「停止の扱い」)。

## 書き戻し

上の「open CL の確かめ」を通してから、次の順で書き戻す。

1. **外す label を先に外す。** 状態の label のうち、呼び出し元の手順が外すと決めたものは、比較より先に `state-label.md` の付け替え方で外す (外す label が無い呼び出し元もある。保証を持たない状態の label (`needs-triage` など) を付けるなら同じ 1 回の操作で付ける)。`ready-for-agent` は、手順 5 の読み直しが済んでから付ける — この順にすると、手順 2 か 5 で止めたときに検査を通っていない本文へ `ready-for-agent` が付いたまま残らない
2. **比べる。** 書き戻す直前に同じコマンドで本文を別の file に保存し、基準の file と diff で比べる (末尾の空白と改行コードの違いは無視する)。食い違えば、他の書き手と競合しているので書き戻さずに止める
3. **書き戻す。** 書き換え後の本文を file に書き、`gh issue edit <N> -R <issue 置き場> --body-file <file>` で書き戻す (題名も変えるなら同じコマンドに `--title <題名>` を足す)
4. **旧本文を記録する。** 次の形のコメントを file に書き、`gh issue comment <N> -R <issue 置き場> --body-file <file>` で投稿する。旧本文は基準の file から写す — context から書き起こすと逐語が崩れる。投稿が失敗したら、基準の file の path を添えて人へ報告し (宛先は呼び出し元の手順が決める)、手順 5 へ進む。親子の関係の記録で親の本文に子の行を足すだけのときは、この手順を飛ばす — 旧本文は書き換えた本文の中に残る

   ```
   旧本文の記録 (現行の仕様ではない)

   <書き換えた理由>

   <details><summary>旧本文</summary>

   <基準の file の中身を逐語で>

   </details>
   ```

5. **読み直す。** 本文をもう一度保存し、手順 3 で書いた file と比べる (末尾の空白と改行コードは無視する)。食い違えば、書き戻しの後に他の書き手が入ったので、以降の操作を止める

## 停止の扱い

「open CL の確かめ」で止めたら、まだ tracker を何も変えていないので、label もそのまま残す。当たった CL の番号と、まだ反映していない操作 (書き換え案と基準の file の path を含む) を、呼び出し元の手順が決めた宛先へ渡す。

手順 2 か 5 で止めたら、以降の操作 (書き換え・label の変更) を行わず、人へ渡す。渡し方は呼び出し元の手順が決め、label を動かしてよいのはその渡し方が決めた付け替え (`needs-info` や `ready-for-human` を付ける等) だけにする。それ以外の label は止めた時点のまま残す (外した label を戻さない・状態の label を付け直さない) — 競合した本文がどの状態に当たるかは、人が本文を読むまで決まらない。渡す内容は次の 4 つ。

- 停止理由 (比較か読み直しのどちらで食い違ったか)
- label の現状 (手順 1 で外した label の一覧)
- まだ反映していない操作
- 次に人がやること (本文と label を確かめ、状態を付け直すか triage をやり直す)

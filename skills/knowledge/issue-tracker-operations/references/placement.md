# issue 置き場と CL 置き場の解決順と、置き場をまたぐ参照

issue 置き場 (issue を読み書きする tracker の場所) と CL 置き場 (CL を読み書きする場所) を決める順。対象 repo は issue の変更が入る repo (cwd の repo) を指し、issue 置き場とは別の repo のことがある。止めたときの宛先と、止めた後にどう続けるかは呼び出し元の手順が決める。

決めた置き場は、コマンドに `-R <issue 置き場>` (CL は `-R <CL 置き場>`) で明示する — cwd に任せると、置き場が cwd と別の repo のとき、同じ番号の別の issue や CL を読み書きする。

issue 置き場と CL 置き場のそれぞれに、同じ次の順を当てる。

1. **呼び出し元の指定。** 呼び出し元が置き場を指定していれば、それを使う
2. **宣言。** 指定が無ければ、対象 repo の `docs/agents/issue-tracker.md` が置き場として宣言する値を使う。宣言が別の file を正本として指していれば (宣言の間接参照)、その file が置き場として宣言する値を使う。CL 置き場を issue 置き場との関係で宣言していれば (「issue 置き場と同じ repo」など)、決めた issue 置き場から導く
3. **読めない宣言では止まる。** 置き場の宣言はあるのに値を読み取れないとき (直接書いた値が読めない・宣言が指す file が無い・その file から値を読み取れない) は、対象 repo 自身へ落とさずに止まり、読もうとした file の path と読めなかった理由を宛先へ渡す — 宣言が別 repo を指していると、対象 repo へ落ちた時点で同じ番号の別の issue や CL を読み書きする
4. **宣言が無いときの既定。** `docs/agents/issue-tracker.md` が無いか、置き場を宣言する記述そのものを持たないときに限り、対象 repo 自身を置き場とする。この既定で決めたことを、呼び出し元へ返す報告に書く — 人が前提を確かめられるように

## 置き場をまたぐ参照の書き方

issue 置き場の外 (CL 置き場など) に投稿する文面が issue を指すときは、`<issue 置き場>#<N>` の形で書く。`<issue 置き場>` は、決めた issue 置き場の値を GitHub なら `owner/repo`、GitLab なら project の full path (`group/project`。subgroup があれば含む) で綴る。二つの置き場が同じ repo でも付ける — 付けておけば、二つの置き場が同じ repo かを確かめずにどの構成でも同じ issue を指す。tracker は素の `#<N>` を、その文面が載った置き場の番号として解決するので、置き場が別の repo だと別の issue を指す。

文面の中の参照を読むときも同じ解決に従う。置き場付きの参照は書かれた置き場の番号、素の `#<N>` はその文面が載った置き場の番号として読み、読んだ置き場を `-R` に渡して引く。
